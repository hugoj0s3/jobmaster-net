# ChangeLog

> **Audience: framework contributors.**
> Documents implementation details, class-level changes, architectural decisions, and bug root causes for each release.
> This file will be kept updated until the stable version, at which point [ChangeLog.md](ChangeLog.md) will be populated from it as the user-facing release notes.

### 0.0.11-alpha
#### Added
- **`JobDefinitionConfig`/`JobDefinitionConfigAttribute`/`IJobMasterSchedulerAdvanced` — publisher/consumer separation for scheduling** (`JobMaster.Abstractions`): lets a publisher schedule a job by referencing only a small shared definition — a `JobDefinitionConfig` (id + config) or a `JobDefinitionConfigAttribute` subclass that carries one — without ever referencing the handler's own assembly. Covers one-time jobs (`OnceNow`/`OnceAt`/`OnceAfter` + `*Async`) and dynamic recurring jobs (`Recurring`/`RecurringAsync`, both expression styles); static schedules got their own, separate attribute-based path instead (see the `RecurringScheduleAttribute` entry below) rather than extending `RecurringScheduleDefinitionCollection.Add<Th>()`'s config-object surface directly.
  - `IJobMasterSchedulerAdvanced` is also now registered directly in DI (`JobMaster\Sdk\ClusterIocRegistration.cs`, `JobMaster\Sdk\Ioc\Setup\ClusterConfigBuilder.cs` — all 4 existing `IJobMasterScheduler` registration sites, main + per-cluster service collections) via `BootstrapBlueprintDefinitions.JobMasterScheduler!.Advanced` (not a cast to the concrete `JobMasterScheduler` type, so it stays correct regardless of the `IJobMasterScheduler` implementation) — a consumer that only needs the `Advanced` surface can inject `IJobMasterSchedulerAdvanced` directly instead of going through `IJobMasterScheduler.Advanced`.
  - ⚠️ **Breaking change, confirmed acceptable**: `Advanced` was added as a non-defaulted member directly on the public `IJobMasterScheduler` interface (`JobMaster\Abstractions\IJobMasterScheduler.cs`), not just on `JobMasterScheduler`/`JobMasterSchedulerClusterAware`. Any external hand-written class implementing `IJobMasterScheduler` directly (not a `Mock<IJobMasterScheduler>` or similar dynamic proxy, which needs no changes) fails to compile (`CS0535`) until it adds an `Advanced` implementation. Documented in `ChangeLog.md`; accepted as low-blast-radius since the interface is designed to be consumed via DI, not hand-implemented.
  - **`JobDefinitionConfig`** (`JobMaster\Abstractions\JobDefinitionConfig.cs`): not sealed (deliberately — lets a user derive their own subclass carrying extra fields, e.g. a `PaymentJobDefinitionConfig` with a `CardType` property). `JobDefinitionId` is a required constructor parameter (throws `ArgumentException` if null/whitespace, no `Type.FullName` fallback like the classic attribute has, since a definition meant for cross-assembly separation shouldn't depend on a type name only the consumer sees); `Priority`/`Timeout`/`MaxNumberOfRetries`/`WorkerLane`/`Metadata` are optional, get-only, set only via constructor. Deliberately not `init`/`required`-property based — the project targets `net8.0;netstandard2.0` with no `IsExternalInit`/`RequiredMemberAttribute` polyfill in the repo, so those C# 9/11 features aren't usable there without one.
  - **`JobDefinitionConfigAttribute`** (`JobMaster\Abstractions\JobDefinitionConfigAttribute.cs`): abstract `Attribute` marker base — no members of its own. `Config` is deliberately **static**, not an instance property: the whole point of `TDefinition`-style scheduling is that publisher and consumer agree on `TDefinition` (the type) as a shared, fixed identity — an instance-derived `Config` would let a subclass with a second constructor produce a different config per application site for the exact same type, silently breaking that contract. A concrete subclass declares its own `public static JobDefinitionConfig Config { get; }` and implements the new **`IStaticJobDefinitionConfig`** (`JobMaster\Abstractions\IStaticJobDefinitionConfig.cs`, mirrors `IStaticRecurringSchedulesProfile`'s shape exactly — `static abstract JobDefinitionConfig Config { get; }` gated `#if NET7_0_OR_GREATER`, empty marker interface on `netstandard2.0`) to have this enforced at compile time on `net8.0`. Tried first having `JobDefinitionConfigAttribute` itself implement `IStaticJobDefinitionConfig` and leave `Config` unimplemented (so subclasses wouldn't need to redeclare the interface) — doesn't compile (`CS0535`): unlike ordinary instance `abstract` members, C# gives no way for a class, even an abstract one, to defer a `static abstract` interface member to its subclasses: it must be implemented directly by any class that declares it implements the interface. So each concrete subclass declares `IStaticJobDefinitionConfig` itself.
    - **Reading `Config`**: since `IStaticRecurringSchedulesProfile`'s own `static abstract` members (`ProfileId`, `Config(...)`) are *never* consumed via compile-time generic dispatch anywhere in the codebase (`JobMasterRuntime.BootstrapStaticRecurringSchedules` always reads them via `Type.GetProperty(..., BindingFlags.Public | BindingFlags.Static)`, since discovery only ever has a `Type` in hand), the same reflection-based approach was used here too, uniformly for both consumption paths — framework-internal discovery from a handler `Type` *and* the scheduler's `TDefinition`-generic methods (where `TDefinition` actually is known at compile time) — rather than adding a second, `#if`-gated code path just for the latter. Two new internal statics on `JobDefinitionConfigAttribute`: `GetConfig(Type definitionType)` (throws `InvalidOperationException` if the type has no static `Config`) and `TryGetAppliedConfig(Type handlerType)` (finds the applied `JobDefinitionConfigAttribute`, if any, and reads its `Config` via `GetConfig`; returns `null` if none applied). `IStaticJobDefinitionConfig`'s only job is forcing the *implementer* to provide `Config` on `net8.0` — the framework itself always uses reflection, exactly like the profile.
  - **`IJobMasterSchedulerAdvanced`** (`JobMaster\Abstractions\IJobMasterSchedulerAdvanced.cs`), exposed via a new `IJobMasterScheduler.Advanced` property: each classic method gets two Advanced siblings — `X<TDefinition>(...)` (generic over the attribute type, keeps the same per-call override params as the classic method — `priority`/`workerLane`/`timeout`/`maxNumberOfRetries`/`metadata` — since `TDefinition`'s config is one fixed value shared by every call site) and `X(JobDefinitionConfig config, ...)` (no override params — the config object is already the caller's to build with whatever values it wants). `TDefinition` is constrained `where TDefinition : JobDefinitionConfigAttribute, IStaticJobDefinitionConfig` (no longer `new()` — dropped along with the instance-based design, since nothing needs to construct a `TDefinition` anymore). `JobMasterScheduler`'s `TDefinition`-generic methods are **explicit interface implementations** (e.g. `JobContext IJobMasterSchedulerAdvanced.OnceNow<TDefinition>(...)`): a single class can't implicitly implement both `IJobMasterScheduler.OnceNow<T>()` (`where T : IJobMasterHandler`) and `IJobMasterSchedulerAdvanced.OnceNow<TDefinition>()` under the same public member name — C# requires matching constraints for implicit implementations (CS0425), and two methods with the same name/arity/parameter-types but different constraints collide outright (CS0111) even across two different implemented interfaces. Explicit implementation sidesteps this since these methods are only reachable through `.Advanced` anyway. A private static `JobMasterScheduler.ApplyOverrides(config, priority, workerLane, timeout, maxNumberOfRetries, metadata)` merges per-call overrides onto a `JobDefinitionConfig` (returns the same instance unchanged if nothing was overridden) before every `TDefinition`-generic method (`ApplyOverrides(JobDefinitionConfigAttribute.GetConfig(typeof(TDefinition)), ...)`) delegates to its config-object sibling.
  - **One-time jobs resolve eagerly, recurring jobs stay deferred — architectural asymmetry preserved deliberately**: `Job.New(clusterId, JobDefinitionConfig config, ...)` (new overload, `JobMaster\Sdk\Abstractions\Jobs\Job.cs`) resolves Priority/Timeout/MaxNumberOfRetries/WorkerLane/Metadata directly from `config` (`?? masterConfig`-default fallback) at schedule time, matching the existing `Job.New<T>()` eager-resolution behavior for one-time jobs. Recurring schedules do not get the equivalent treatment: `RecurringSchedule.New(clusterId, JobDefinitionConfig config, ...)` (new overload, `RecurringSchedule.cs`) passes `config`'s values straight through to the existing non-generic `RecurringSchedule.New(clusterId, jobDefinitionId, ...)` with **no** eager cluster-default resolution, exactly like `RecurringSchedule.New<T>()` already does today — because recurring schedules defer all Priority/Timeout/MaxNumberOfRetries/WorkerLane resolution to replan time (`RecurringSchedulePlanner.ScheduleNextJobsAsync` → `Job.FromRecurringSchedule` → `Job.New(Type-based)` → `JobUtil.Get*`), by design, so a long-lived schedule picks up config/attribute/cluster-default changes on its next occurrence rather than freezing them in at creation. Making this fix correct at replan time required extending `JobUtil.GetTimeout`/`GetWorkerLane`/`GetMaxNumberOfRetries`/`GetJobMasterPriority` (`JobMaster\Sdk\Abstractions\Jobs\JobUtil.cs`) to check for a `JobDefinitionConfigAttribute` on the handler type first (via `JobDefinitionConfigAttribute.TryGetAppliedConfig`), before the classic individual attributes (`[JobMasterTimeout]` etc.) — otherwise a recurring schedule targeting a definition-mode handler would silently fall back to cluster defaults on every occurrence, since its config lives in the attribute's static `Config`, not as individual attributes on the handler class.
  - **ID resolution consolidated onto one method, attribute-family-aware**: `JobMasterDefinitionIdAttribute.GetJobDefinitionId(Type)`/`GetJobHandlerTypeFromId(string)` (`JobMaster\Abstractions\Models\Attributes\JobMasterDefinitionIdAttribute.cs`) now check for a `JobDefinitionConfigAttribute` first (via `JobDefinitionConfigAttribute.TryGetAppliedConfig(type)?.JobDefinitionId`), then fall back to the classic `[JobMasterDefinitionId]`/`Type.FullName`. `JobUtil.GetJobDefinitionId` and `RecurringSchedule.New<T>()` (previously each had their own near-duplicate inlined copy of the classic-attribute-or-FullName logic) now delegate to this one method instead, so the classic generic paths (`OnceNow<THandler>()`, `Recurring<THandler>()`) also correctly resolve a `JobDefinitionConfigAttribute` if a handler happens to carry one instead of `[JobMasterDefinitionId]`.
  - **Startup validation against mixing the two attribute families on one handler** (`DefaultRuntimeValidatorSetup.ValidateAsync`, see Fixed below for why this can now actually stop startup): a handler carrying both a `JobDefinitionConfigAttribute` and any classic individual attribute (`JobMasterDefinitionId`/`JobMasterTimeout`/`JobMasterPriority`/`JobMasterWorkerLane`/`JobMasterMaxNumberOfRetries`) reports a validation error — mixing almost always means a stale attribute left over from switching modes, and silently picking a winner (config was winning, since it's checked first in every resolver above) would hide that mistake rather than surface it.
  - **Startup validation against a missing static `Config`** (`DefaultRuntimeValidatorSetup.ValidateAsync`), added after Hugo asked for it explicitly ("especially good for netstandard"): scans every loaded assembly for non-abstract types implementing `IStaticJobDefinitionConfig` and checks each one via the new `JobDefinitionConfigAttribute.TryGetConfig(Type, out JobDefinitionConfig?)` (non-throwing sibling of `GetConfig`, which now delegates to it). Any violators are reported as one aggregated message naming every offending type, **and the method returns early** before computing `handlerTypes` below — that block resolves `JobDefinitionId` via `JobMasterDefinitionIdAttribute.GetJobDefinitionId` → `JobDefinitionConfigAttribute.TryGetAppliedConfig` → `GetConfig`, which would otherwise throw uncaught partway through discovery (crashing startup with a raw, non-aggregated exception) instead of reporting cleanly like every other check in this method. This is the only thing that catches a missing `Config` on `netstandard2.0`, where `IStaticJobDefinitionConfig.Config` isn't compiler-enforced. Not unit tested directly (no check in this class ever has been — it scans process-wide `AppDomain`/static state, which doesn't isolate cleanly per test; a first attempt at testing it directly, by decorating an `IJobMasterHandler` test fixture with a broken definition attribute, broke 4 unrelated tests in `JobsExecutionEngineTests` for exactly this reason — `JobMasterDefinitionIdAttribute.GetJobHandlerTypeFromId`'s own `AppDomain`-wide scan evaluated the broken fixture unconditionally). Covered instead by direct `TryGetConfig` unit tests (`Tests\JobMaster.UnitTests\Abstractions\JobDefinitionConfigAttributeTests.cs`) plus the two live scenario tests exercising real startup end-to-end.

- **`RecurringScheduleAttribute`/`NaturalCronScheduleAttribute`/`TimeSpanIntervalScheduleAttribute` — attribute-based static recurring schedules** (`JobMaster\Abstractions\StaticRecurringSchedules\`): a lighter alternative to `IStaticRecurringSchedulesProfile` for the common case of one handler with one (or a few) fixed schedules — decorate the handler class directly, e.g. `[NaturalCronSchedule("every 6 minutes")]` on an `IJobMasterHandler`, no profile class needed. Purely an additional registration path feeding the exact same static-schedule machinery profiles already use (same upsert, reconciliation, keep-alive) — not a new scheduling feature.
  - **`RecurringScheduleAttribute`** is abstract (`[AttributeUsage(AttributeTargets.Class, AllowMultiple = true)]`), carrying `Expression` (ctor param, get-only) and an `abstract string ExpressionTypeId { get; }` — an ordinary instance property, unlike `JobDefinitionConfigAttribute.Config` (see above), since a `RecurringScheduleAttribute` instance is only ever discovered by scanning a handler class for applied attributes, never referenced via a `TDefinition`-style generic type parameter — so there's no publisher/consumer identity contract for a per-instance value to silently violate, and an ordinary instance abstract member (which *can* be deferred through an abstract base class, unlike `static abstract`) is simpler. `AllowMultiple = true` so one handler can carry more than one schedule; `GenerateUniqueId`'s existing collision-numbering (`-1`, `-2`, ...) already disambiguates the resulting static-schedule IDs for free, no extra work needed. `NaturalCronScheduleAttribute`/`TimeSpanIntervalScheduleAttribute` are the two built-in subclasses, each just wiring `ExpressionTypeId` to the matching compiler's own public `TypeId` const (`NaturalCronExprCompiler.TypeId`/`TimeSpanIntervalExprCompiler.TypeId`) rather than re-hardcoding the string — a third party's own `IRecurrenceExprCompiler` (registered via `RecurrenceCompilerFactory.RegisterCompiler`) can supply its own `RecurringScheduleAttribute` subclass the same way.
  - **v1 scope, confirmed with Hugo**: no per-attribute `ClusterId`/`WorkerLane` (registers to the default cluster only); `WorkerLane`/`Priority`/`Timeout`/`MaxNumberOfRetries` are left `null` on the resulting `StaticRecurringScheduleDefinition` and resolved from the handler's own `[JobMasterWorkerLane]`/`[JobMasterPriority]`/etc. (or `JobDefinitionConfigAttribute`) at replan time via `JobUtil.Get*` — the exact same deferred-resolution behavior the dynamic `Advanced.Recurring<TDefinition>` path already relies on, and for the same reason (a long-lived schedule should pick up config changes on its next occurrence, not freeze them in at registration).
  - **`RecurringScheduleDefinitionCollection` (`JobMaster\Abstractions\StaticRecurringSchedules\RecurringScheduleDefinitionCollection.cs`) gained `Type`-based `Add(Type handlerType, ...)` overloads** (both the text-expression and pre-compiled-expression shapes) alongside the existing generic `Add<Th>()` ones, which now just delegate (`Add<Th>(...) => Add(typeof(Th), ...)`) — needed because the new attribute scan only has a runtime `Type`, not a compile-time `Th`. The `Type`-based `Add` validates `typeof(IJobMasterHandler).IsAssignableFrom(handlerType)` itself (the generic overload got this for free from its `where Th : class, IJobMasterHandler` constraint). Fixed a related pre-existing bug while touching this method: `JobDefinitionId` resolution used a narrow inline check (`typeof(Th).GetCustomAttribute<JobMasterDefinitionIdAttribute>()?.JobDefinitionId ?? typeof(Th).FullName!`) instead of the shared `JobMasterDefinitionIdAttribute.GetJobDefinitionId(Type)` helper every other path already uses — meaning a handler using `JobDefinitionConfigAttribute` got a different (wrong) `JobDefinitionId` when registered via a static profile than when scheduled dynamically. Now routes through the shared helper, matching every other path. (`GenerateUniqueId`'s own `defId` fallback, which uses `handler.Name` rather than `FullName`, is a separate, smaller inconsistency — left as-is, out of scope.)
  - **`JobMasterRuntime.BootstrapStaticRecurringSchedules`** (`JobMaster\Sdk\Background\JobMasterRuntime.cs:645-754`) gained a second discovery loop, appending to the exact same `profileInfos` list the profile-discovery loop already builds: scans `AppDomain.CurrentDomain.GetAssemblies()` for non-abstract types carrying a `RecurringScheduleAttribute` (mirroring `JobMasterIocRegistrationAttribute`'s existing attribute-scan pattern, rather than the profile loop's interface-name-string match), throws `InvalidOperationException` if a decorated type doesn't implement `IJobMasterHandler`, and synthesizes one `StaticRecurringSchedulesProfileInfo`/`RecurringScheduleDefinitionCollection` pair per handler with `ProfileId = "attr:{JobMasterDefinitionIdAttribute.GetJobDefinitionId(handlerType)}"` — deterministic across restarts (required, since it feeds `GenerateUniqueId`'s composite `"{clusterId}:{profileId}:{defId}"` static-schedule ID, and a changing ID would orphan the old row on every restart). Everything downstream (disabled-priority validation, per-cluster upsert, distributed locking, `StaticRecurringDefinitionIdsKeeper` registration, the 1-minute keep-alive runner) is reused completely unchanged, since both loops just populate the same list.
  - Verified end-to-end against a real cluster: extended `Tests\JobMaster.ScenarioTests\Scenarios\RecurringScheduleTest\RecurringScheduleTestPhase1EmulatorBase.cs` with a 5th combo (`AttributeStaticTickHandler` in `TargetTestRecurringApp`, `[TimeSpanIntervalSchedule("00:06:00")]`, no profile, no `/recurring-schedule` endpoint call needed at all) — `RecurringScheduleTest.PostgresPure` passes with all 5 combos (2 profile-based static, 1 attribute-based static, 2 dynamic) firing correctly.

#### Fixed
- **`DefaultRuntimeValidatorSetup.ValidateAsync`'s "workers without `AgentConnectionName`" check didn't exempt Coordinator-mode workers** (`JobMaster\Sdk\Background\DefaultRuntimeValidatorSetup.cs`): a `Coordinator`-mode worker is *supposed* to have no `AgentConnectionName` (see the `AgentConnectionId` nullable-for-Coordinator entry above — configuring one now throws, the opposite problem) — but this check flagged the opposite case, any worker *lacking* one, without excluding `Coordinator`. Like the two entries above, this had no effect until the `JobMasterRuntime.StartAsync` discard-bug fix (below) made validation results actually throw for the first time — at which point *every* cluster with a Coordinator worker started failing startup. Root-caused live while adding scenario-test coverage for `Advanced` scheduling: `ScheduleTest.PostgresPure`'s Phase 2/3 containers (which introduce a Coordinator worker, `Tests\JobMaster.ScenarioTests\Scenarios\ScheduleTest\PostgresPure\Phase2\postgres-dist-one.json`) started failing their readiness check with exit code 139 (SIGSEGV) — traced to `StartJobMasterRuntimeAsync()` throwing an unhandled exception during container startup, before the HTTP port ever bound; the SIGSEGV itself is consistent with the known .NET-in-Docker pattern where the crash-dump generator (`createdump`) faults on an unhandled exception in a constrained container, rather than the exception's own exit code surfacing directly. Confirmed via `git stash`-based bisection (baseline without the throw-fix passed cleanly; with it, failed consistently at the same Phase 1→2 transition) before finding the actual root cause. Fixed by excluding `Mode == AgentWorkerMode.Coordinator` from the check.
- **`JobMasterRuntime.StartAsync` discarded every `IJobMasterRuntimeSetup.ValidateAsync` result — validation never actually stopped startup** (`JobMaster\Sdk\Background\JobMasterRuntime.cs`): the loop called `await runtimeSetup.ValidateAsync(scope.ServiceProvider)` for every registered setup but never captured or checked the returned `IList<string>` of error messages. This meant `DefaultRuntimeValidatorSetup`'s existing checks (duplicate `JobDefinitionId` across handlers, workers missing `AgentConnectionName`) and `NatsJetStreamJobMasterRuntimeSetup`'s checks (agent connection referencing a nonexistent cluster, `TransientThreshold` exceeding the NATS cap) had never been able to stop a misconfigured startup — they computed real messages, then those messages went nowhere. `StartAsync` now aggregates every setup's messages and throws `InvalidOperationException` (joining them, one per line) if any are non-empty, before `PreValidation()`/`OnBeforeStartAsync` run. Audited all 4 `IJobMasterRuntimeSetup.ValidateAsync` implementations in the repo (`DefaultRuntimeValidatorSetup`, `RavenDbJobMasterRuntimeSetup`, `NatsJetStreamJobMasterRuntimeSetup`, `SqlJobMasterRuntimeSetup`) before making this throw for real: RavenDb's and SqlBase's (and its Postgres/SqlServer/MySql subclasses, none of which override it) are hardcoded no-ops that can never return a non-empty list; the two with real logic only ever report genuine misconfigurations, never something that would legitimately occur on a healthy startup — so this is safe for existing working deployments and will only newly throw for configurations that already had a real, previously-silently-ignored problem.
- **`DefaultRuntimeValidatorSetup.ValidateAsync`: `TransientThreshold > 24h` check was permanently dead, and swallowed the other two checks whenever it would have fired** (`JobMaster\Sdk\Background\DefaultRuntimeValidatorSetup.cs`): the method computed `clustersWithTransientThresholdGreaterThan24Hours` then did `if (clustersWithTransientThresholdGreaterThan24Hours.Any()) return Task.FromResult<IList<string>>(new List<string>());` — i.e. when a real violation existed (`Any()` true), it returned an **empty** list immediately, discarding the real error and skipping the duplicate-`JobDefinitionId`/missing-`AgentConnectionName` checks entirely; when no violation existed (`Any()` false), the `foreach` below it iterated zero times by construction, so its `result.Add(...)` could never execute either way. Net effect: this specific check could never report anything, under any configuration, ever. Fixed by removing the inverted early return and materializing the query once (`.ToList()`) before the `foreach`.
- **`MasterJobsService.ValidateJobExecutionOutcome`: retrying a failed job with attempts remaining threw `ArgumentException`** (`JobMaster\Sdk\Services\Master\MasterJobsService.cs`): `JobRawModel.TryRetry()` sets `Status` back to `OnMaster` — not `Failed` — when `NumberOfFailures < MaxNumberOfRetries`, since the job is meant to be picked up fresh from the master queue for another attempt. But the validation guard only accepted a `Failed` `JobExecution.Outcome` when the job's own `Status` was also `Failed`, so calling `UpdateAsync`/`Update` with the failed attempt's execution record and the retried (now `OnMaster`) job always threw — meaning persisting a failed-but-retrying job through this path was broken.
  - First fix pass added `Status == OnMaster` as a second accepted status alongside `Status == Failed` for a non-`Succeeded` outcome, leaving every other status (`InBucket`, etc.) still rejected — this was the version originally documented here.
  - **Simplified further, after this changelog entry was first written** (Hugo, directly in `MasterJobsService.cs`): rather than enumerating every status a `Failed` outcome is allowed alongside, the guard now only cross-validates the two statuses where job status and execution outcome have a genuine 1:1 relationship — `Status == Succeeded` requires `Outcome == Succeeded`, and `Status == Failed` requires `Outcome == Failed`. Every other status (`OnMaster`, `InBucket`, etc.) now accepts any execution outcome unconditionally; there is no longer a case where a non-`Succeeded`/non-`Failed` status combined with a `Failed` outcome throws. This is the actual, final behavior — the two-status enumeration above is superseded.
  - Covered by tests in `Tests\JobMaster.UnitTests\Services\Master\MasterJobsServiceTests.cs` (first test file for this class): the `OnMaster`+`Failed` combination passes (fixing the original bug), and `UpdateAsync_WhenJobIsInBucketWithFailedExecution_ShouldThrowArgumentException` was renamed to `UpdateAsync_WhenJobIsInBucketWithFailedExecution_ShouldNotThrow` and its assertion flipped to match the simplified rule (confirmed with Hugo this is a deliberate, permanent loosening, not a regression to re-flag).
- **`MasterJobsService.AcquireAndFetchAsync`: a SQL deadlock during acquire now returns no jobs instead of retrying then throwing** (`JobMaster\Sdk\Services\Master\MasterJobsService.cs`): previously wrapped in `RetryDeadlockPolicy` (3 retries, jittered 250-375ms backoff) before letting a persistent deadlock propagate as an exception; the constructor's `IJobMasterRuntime runtime` dependency and that policy field were both removed as part of this (throttler now comes from `OperationThrottlerSettingsFactory.GetMasterThrottler`, see the throttler entry above). Now catches the deadlock directly (`exceptionIdentifier.Identify(ex) == JobMasterKnownExceptionId.Deadlock`) and returns `Array.Empty<JobRawModel>()` — a deadlocked claim transaction rolls back before committing any row locks, so no job was actually acquired under that `partitionLockId`, functionally identical to a tick that found nothing ready; the caller's normal poll-and-retry-next-tick behavior already handles that case, so there's no need to surface an exception for an outcome the system already treats as routine elsewhere. `MasterRecurringSchedulesService` was **not** changed the same way — it still uses `RetryDeadlockPolicy` as before; this fix is scoped to `MasterJobsService.AcquireAndFetchAsync` specifically. Covered by new tests in `Tests\JobMaster.UnitTests\Services\Master\MasterJobsServiceTests.cs` (deadlock → empty list; non-deadlock exception → still propagates, confirming the catch is scoped to the identified deadlock case only).
- **Repository-type-driven throttling and batch sizing** (new `JobMaster.Sdk.Abstractions.Repositories.OperationThrottlerSettingsTemplateFactory`, `OperationThrottlerSettingsTemplate`, `OperationThrottlerSettingsFactory`): replaces the previous per-connection `RuntimeDbOperationLimit` setting and the single global `JobMasterConstants.MaxBatchSizeForBulkOperation = 50` constant with settings scoped to *repository type* (`"Postgres"`, `"MySql"`, `"SqlServer"`, `"RavenDb"`, `"NatsJetStream"`), registered once per provider at startup instead of duplicated per connection or hardcoded globally.
  - **`OperationThrottlerSettingsTemplateFactory`** is the repository-type-level registry: `RegisterForMaster(repositoryTypeId, maxBatchSize, throttlerSettingsTemplate)` and `RegisterForAgent(repositoryTypeId, maxBatchSize, internalThrottlerSettingsTemplate, schedulingThrottlerSettingsTemplate)` store a `MasterEntry`/`AgentEntry` per repository type (private nested classes), each guarded by the same `JobMasterRuntimeSingleton.Instance.Started` check `RepositoryGuard`'s original scaffold used. `GetMasterMaxBatchSize(repositoryTypeId)`/`GetAgentMaxBatchSize(repositoryTypeId)` read the current entry directly (no caching beyond the dictionary itself, so a `Register*` call always takes effect immediately for `MaxBatchSize`, even for a repository type already queried earlier). `GetMasterThrottlerTemplate`/`GetInternalAgentThrottlerTemplate`/`GetSchedulingAgentThrottlerTemplate` are `internal` (not `public`) — exposed only for `OperationThrottlerSettingsFactory` to mint live throttlers from, never meant to be called directly. An unregistered repository type falls back to a generic default (`maxBatchSize: 50`, master capacity 50, internal-agent capacity 25, scheduling-agent capacity 10/500ms), cached on first miss so the default itself is stable too.
  - **`OperationThrottlerSettingsTemplate`** is a sealed value type holding just `capacity`/`acquireTimeoutMs` with a `Create()` method that always returns a brand-new `OperationThrottler`. Deliberately not the `OperationThrottler` instance itself (an earlier draft based on a strategy-interface `IOperationThrottlerFactory` was simplified away since there's only one implementation) — storing a live-but-never-executed `OperationThrottler` as a "template" would be one call away from being misused directly.
  - **`OperationThrottlerSettingsFactory`** is the facade every real consumer actually calls: `GetMasterThrottler(clusterId)`, `GetInternalAgentThrottler(agentConnectionId)`, `GetSchedulingAgentThrottler(agentConnectionId)`, `GetMasterMaxBatchSize(clusterId)`, `GetAgentMaxBatchSize(agentConnectionId)`. It resolves the caller's connection identity down to a repository type id internally (`JobMasterClusterConnectionConfig.Get(clusterId).RepositoryTypeId` for the master role; for the two agent-facing roles, `new AgentConnectionId(agentConnectionId)` splits the `"{clusterId}:{name}"` id back apart — the same parsing `AgentConnectionId.IsValid()` already relies on — then `.GetAgentConnectionConfig(name).RepositoryTypeId`) so callers never resolve or pass a repository type id themselves. Live `OperationThrottler` instances are cached per **connection identity** (`ConcurrentDictionary<string, OperationThrottler>`, one dictionary per role, keyed by `clusterId`/`agentConnectionId`), deliberately *not* per repository type — two independent connections of the same repository type (e.g. two separate NatsJetStream agent connections) each get their own throttler/semaphore, never sharing one, since sharing would silently halve (or worse) each connection's real concurrency budget.
  - **Pre-`Started` safety net**: providers register their real settings in `OnBeforeStartAsync`, which always completes before `JobMasterRuntimeSingleton.Instance.Started` flips true — but before that point, nothing guarantees a given repository type's real settings are registered yet. All five public methods on `OperationThrottlerSettingsFactory` check `Started` first: before it flips, `Get*Throttler` return a single shared `NotStartedThrottler = new OperationThrottler(3, 250)` (uncached, and identical across all three roles — deliberately tiny, since startup is a narrow, low-traffic window where a small shared concurrency budget is the safer default regardless of role or repository type) and `Get*MaxBatchSize` return a `NotStartedMaxBatchSize = 3` constant, without ever attempting to resolve a repository type id at all. This matters for two reasons: (1) caching a throttler under the real connection key before `Started` would permanently stick that connection with a possibly-generic-default capacity forever, since the per-connection cache is a `GetOrAdd` that never re-reads the template after first build; (2) resolving an agent connection's repository type id pre-`Started` could throw `KeyNotFoundException` if that specific connection hasn't been registered on `JobMasterClusterConnectionConfig` yet, which the shared not-started fallback sidesteps entirely by never attempting the lookup.
  - **Per-provider registered values** (all set in each provider's `*JobMasterRuntimeSetup.OnBeforeStartAsync`, first statement(s), before any other provisioning work): Postgres — master maxBatchSize 50/capacity 50, agent maxBatchSize 50/internal capacity 25/scheduling (10, 500ms). SqlServer — same as Postgres. MySql — master maxBatchSize 50/capacity 5, agent maxBatchSize 50/internal capacity 5/scheduling (5, 500ms). RavenDB — master maxBatchSize 500/capacity (10, 5000ms), agent maxBatchSize 500/internal (5, 2500ms)/scheduling (5, 250ms). NatsJetStream — agent-only (never registers master settings, since NATS is never a cluster/master repository type), maxBatchSize 50/internal (250, 1000ms)/scheduling (100, 125ms).

- **RavenDB connection options: `requestTimeout`, `pooledConnectionLifetime`, `pooledConnectionIdleTimeout`** (`JobMaster.RavenDb`): three new optional settings on `UseRavenDb` (both the master/cluster and agent fluent overloads, appended after every pre-existing parameter) and their `ConfigFromJson` counterparts on `RavenDbConnectionOptionsBinder` (`requestTimeoutMs`/`pooledConnectionLifetimeMs`/`pooledConnectionIdleTimeoutMs`, all integer milliseconds). - **`ConfigFromJson` — JSON DTOs and connection-options plugin mechanism** (`JobMaster.Sdk.Ioc.Setup.Json`, `JobMaster.Sdk.Abstractions.Ioc`): three internal binding DTOs — `ClusterJsonConfig`, `AgentConnectionJsonConfig`, `WorkerJsonConfig` — mirror the fluent selector surface (cluster settings, `DisabledPriorities`, `AgentConnections`, `Workers`, each with an optional `ConnectionOptions: Dictionary<string, object>`). `ClusterConfigBuilder.ConfigFromJson(IConfiguration)`/`(string jsonOrFilePath)`/`(Stream)` bind/deserialize into `ClusterJsonConfig` and hand off to `ApplyJsonConfig`. Provider-specific `ConnectionOptions` (e.g. NATS auth/TLS keys) are applied through a new plugin interface, `IConnectionOptionsStrategy` (`SetOptions` for both `IClusterConfigSelector` and `IAgentConnectionConfigSelector`), keyed by `RepoType`. `ConnectionOptionsStrategyFactory.Discover()` reflects over all loaded, non-dynamic assemblies at static-init time for concrete parameterless-constructible `IConnectionOptionsStrategy` implementations and indexes them by `RepoType`; `Create(repoType)` throws `InvalidOperationException` if no strategy is registered for the given repo type (e.g. provider assembly not referenced). `NatsJetStreamConnectionOptionsStrategy` is the first implementation: validates every options key against a known-key allowlist (throws `ArgumentException` on an unrecognized key), builds `NatsAuthOpts` from `username`/`password`/`token`/`credentialsFile`/`nkey`/`jwt`, and `NatsTlsOpts` from `tlsCertBundleFile`/`tlsCertBundleFilePassword`/`tlsCaFile`/`tlsInsecureSkipVerify`/`tlsMode` (parsed as `TlsMode`, throws `ArgumentException` on an invalid value) — both appended via `AppendAdditionalConnConfigValue`. Its `SetOptions(IClusterConfigSelector, ...)` overload always throws, since NATS JetStream isn't supported as a cluster master repository.

- **`AddJobMasterClusterForApi` — two overloads** (`JobMaster.Api`, `JobMasterClusterApiExtensions`): wraps the existing `AddJobMasterCluster` overloads and restricts the callback to `Action<IBaseClusterConfigSelector<IClusterConfigSelector>>`, preventing accidental worker/handler registration in API-only deployments. After calling `configure(selector)`, `EnsureApiDefaultSet` checks `BootstrapBlueprintDefinitions.Clusters.Any(c => c.IsDefault)` — if nothing has claimed default yet, the current selector calls `SetAsDefault()`. This means the first `AddJobMasterClusterForApi` call silently becomes the default, and all subsequent ones skip the check. The comment on `EnsureApiDefaultSet` documents the rationale: API routing is always cluster-ID-explicit, so the "default" is never consulted in practice, but the runtime's `PreValidation` still requires one cluster to be marked default when multiple are registered.

- **Reserved `master-fallback-agent-conn` agent connection** (`JobMasterConstants`, `JobMasterClusterConnectionConfig`): new `AddMasterFallbackAgentConnectionString()` lazily registers a connection that reuses the cluster's own connection string/repository type, the same pattern already used for the standalone connection (`AddStandaloneAgentConnectionString`). Resolved automatically via `TryGetAgentConnectionConfig` and reserved against use by real agents in `JobMasterRuntime.PreValidation`. - **`AgentWorkerModeExtensions.Is(AgentWorkerMode)`** (`JobMaster.Abstractions.Models`): `Full` satisfies checks for `Coordinator` (and any other mode) since it also runs those runners. Replaces the ad-hoc `mode == Coordinator || mode == Full` comparisons in `WorkerClusterOperations.CountActiveCoordinatorWorkersAsync` and the new bootstrap-time fallback-connection registration in `JobMasterRuntime`.
- **`IClusterConfigSelector.DataRetentionTtl(TimeSpan)` / `RetainDataForever()` / `IClusterStandaloneConfigSelector.ClusterDataRetentionTtl(TimeSpan)` / `ClusterRetainDataForever()`**: the cluster-wide data retention TTL can now be set at bootstrap time via the fluent selector and `ConfigFromJson`. `RetainDataForever()` sets `TimeSpan.Zero` explicitly and is an alias for `DataRetentionTtl(TimeSpan.Zero)`. `DataRetentionTtl(TimeSpan)` validates: if `value > Zero && value < JobMasterDefaults.MinDataRetentionTtl` (10 minutes) it throws `ArgumentException`; zero or negative is normalized to `TimeSpan.Zero`. `ClusterDefinition.DataRetentionTtl` stays `TimeSpan?` (null = not configured by user code) and merges via the usual `??` in `JobMasterRuntime.StartAsync`: `modelToSave.DataRetentionTtl = clusterDefinition.DataRetentionTtl ?? modelToSave.DataRetentionTtl`. `ClusterConfigurationModel.DataRetentionTtl` is now non-nullable `TimeSpan` (was `TimeSpan?`); `TimeSpan.Zero` is the "infinite / no purge" sentinel — this is backward-safe because normal code always initialized the field before persisting. `JobMasterDefaults.DataRetentionTtl` changed from 30 days to `TimeSpan.Zero` (infinite), preparatory for a future archive-cluster feature where archive clusters must not auto-delete data by default. `JobMasterDefaults.MinDataRetentionTtl = TimeSpan.FromMinutes(10)` added as the lower bound on positive TTLs.
- **Adaptive `SucceedInterval` on cleanup runners** (`DeleteOldFinalJobsRunner`, `DeleteOldLogsRunner`, `DeleteOldInactiveRecurringSchedulesRunner`): all three runners now compute `SucceedInterval` dynamically from `clusterConfigService.Get()` (cached, cheap) each time the property is accessed — using `Clamp(TTL/2, 5 min, 1 hr)` via `Math.Max`/`Math.Min` (netstandard2.0 has no `Math.Clamp(long)`). When TTL ≤ zero (infinite), the interval falls back to 1 hour (the runner will skip its tick anyway). `burstNext` standardized to 1 minute on all three runners. Rationale: a fixed interval (e.g. 5 min) under a short TTL (e.g. 10 min) ran cleanup at TTL/1 — half the window — producing unnecessary load; `TTL/2` keeps pace with how fast the backlog accumulates while staying within the retention guarantee.

- **Auto-archive feature** — finalized jobs/terminated recurring schedules are moved to a separate `ClusterMode.Archived` cluster before being purged, instead of hard-deleted. Builds directly on the `DataRetentionTtl`/`ClusterMode.Archived` groundwork above.
  - **Config surface** (`ClusterDefinition`, `IClusterConfigSelector`, `IClusterStandaloneConfigSelector`, `ClusterConfigBuilder`, `ClusterJsonConfig`, `ClusterConfigurationModel`): `DataRetentionTtl`/`ClusterDataRetentionTtl` gained an optional `string? targetArchivedClusterId = null` param (default keeps every existing call site compiling). `ClusterDefinition.SetDataRetentionTtl` (the method both selectors already shared) now also assigns the new `ClusterDefinition.TargetArchivedClusterId` / `ClusterJsonConfig.TargetArchivedClusterId` / `ClusterConfigurationModel.TargetArchivedClusterId` (persisted, merged in `JobMasterRuntime.StartAsync` the same `??` way as every other cluster setting). Named `TargetArchivedClusterId` (not `ArchivedClusterId`) specifically to read as "where this cluster archives *to*", not "this cluster's own archive state".
  - **Startup validation, synchronous** (`JobMasterRuntime.PreValidation`): added next to the existing "Passive and Archived clusters can not have buckets defined" check — an `Archived` cluster can't have agent connections defined, can't have non-Coordinator workers, can't reference itself as `TargetArchivedClusterId`, and if `TargetArchivedClusterId` is set it must resolve (via `BootstrapBlueprintDefinitions.Clusters`, not just a bare id match against connection configs) to a cluster definition whose own `ClusterMode == ClusterMode.Archived` — pointing at a non-archive cluster is rejected at boot, not just a nonexistent one.
  - **Startup validation, async** (`JobMasterRuntime.StartAsync`, per-cluster loop, right after `masterConfigService.Save(modelToSave)`): if the cluster resolves to `ClusterMode.Archived`, queries its own `IMasterJobsRepository`/`IMasterRecurringSchedulesRepository` for any row in a non-final status (`Enum.GetValues(typeof(JobMasterJobStatus)).Cast<JobMasterJobStatus>().Where(!IsFinalStatus)` for jobs; loops the non-final `RecurringScheduleStatus` values individually since `RecurringScheduleQueryCriteria` only supports a single `Status`) and throws if it finds one — guards against an archive cluster being fed live data by anything other than the archive path below.
  - **Repository layer** (`IMasterJobsRepository`/`SqlMasterJobsRepository`, `IMasterRecurringSchedulesRepository`/`SqlMasterRecurringSchedulesRepository`): each gained `BulkInsertIfNotExistsAsync`, `QueryFinalizedToPurgeAsync`/`QueryTerminatedToPurgeAsync`, and `DeleteByIdsAsync`. `PurgeFinalizedAsync`/`PurgeTerminatedAsync` were refactored from one combined select+delete transaction into `select ids → DeleteByIdsAsync(ids)`, with no change to external behavior or performance for clusters with no archive target. `QueryFinalizedToPurgeAsync`/`QueryTerminatedToPurgeAsync` mirror the same candidate WHERE/ORDER-BY as the purge methods but hydrate full rows (same `jobs_page`/`schedules_page` CTE-then-join-metadata shape already used by `BuildQuerySql`) instead of just ids, for the archive path. `BulkInsertIfNotExistsAsync` is `virtual` and ANSI-portable: batches at `JobMasterConstants.MaxBatchSizeForBulkOperation` (50), building one `INSERT INTO t (cols) SELECT ... WHERE NOT EXISTS (SELECT 1 FROM t WHERE cluster_id=@ClusterId_i AND id=@Id_i) UNION ALL SELECT ...` per batch (per-row-suffixed `DynamicParameters`, same pattern as `SqlMasterLogsRepository.BuildBulkInsertSql`), giving every row a fresh `Version`. Deliberately left as the portable base implementation only — provider-specific `ON CONFLICT DO NOTHING` (Postgres)/`INSERT IGNORE` (MySql)/`MERGE` (SqlServer) overrides are an intentional follow-up, not part of this change.
  - **Cross-cluster resolution** (`JobMasterClusterAwareComponentFactories`): added `TryGetFactory(string clusterId)` returning `IJobMasterClusterAwareComponentFactory?` (null if not registered) alongside the existing throwing `GetFactory` — matches the nullable-return `TryGet` convention already used by `JobMasterClusterConnectionConfig.TryGet`/`SqlGenerator.TryGet` (an initial `bool TryGetFactory(id, out factory)` draft was rejected in review for not matching this).
  - **Archive services** (new `IMasterJobArchiveService`/`MasterJobArchiveService`, `IMasterRecurringScheduleArchiveService`/`MasterRecurringScheduleArchiveService`, registered in `ClusterConfigBuilder` alongside the other `AddJobMasterComponent<...>()` calls): every cluster gets its own instance (ordinary per-cluster component), but only the *archive* cluster's instance is ever invoked, resolved cross-cluster via `JobMasterClusterAwareComponentFactories.TryGetFactory(targetArchivedClusterId)?.GetComponent<IMasterJobArchiveService>()`. The service doesn't need to know `TargetArchivedClusterId` itself — that lookup is the caller's job; the service just validates every incoming row is `IsFinalStatus()` (throws otherwise — defense in depth), reassigns each to its own cluster (new `JobRawModel.ReassignToArchiveCluster`/`RecurringScheduleRawModel.ReassignToArchiveCluster`, mirroring the existing `SetVersion` pattern, since `ClusterId` has a `protected` setter), and calls its own injected repository's `BulkInsertIfNotExistsAsync` — same-cluster DI throughout, no repository is ever touched across a cluster boundary directly.
  - **Runner wiring** (`DeleteOldFinalJobsRunner`, `DeleteOldInactiveRecurringSchedulesRunner`): when `cfg.TargetArchivedClusterId` is set and its factory resolves, the tick does `QueryFinalizedToPurgeAsync`/`QueryTerminatedToPurgeAsync` → `archiveService.BulkInsertIfNotExistsAsync(candidates)` → `DeleteByIdsAsync(ids)`; otherwise it's the unchanged `PurgeFinalizedAsync`/`PurgeTerminatedAsync` fast path. Archive-then-delete as two independent transactions (not delete-first-with-rollback-on-archive-failure) was a deliberate choice over holding a source-cluster DB transaction open across the cross-cluster network call to the archive service (long-held-lock/connection-pool risk); safety instead comes from `BulkInsertIfNotExistsAsync`'s idempotency — a crash between archive-commit and delete just means the next tick re-archives a no-op and retries the delete, so nothing is duplicated or lost. When a `TargetArchivedClusterId` is configured but its factory can't be resolved (the process this cluster is running in doesn't have that cluster registered/reachable), the runner logs `logger.Critical(..., JobMasterLogCategory.Cluster, BackgroundAgentWorker.ClusterConnConfig.ClusterId)` every tick before falling back to a plain delete — this is an explicit "you are losing data" signal rather than a silent fallback, since the whole point of configuring archiving is that nothing should be deleted unarchived.
  - **Trimmed runner set for archive-mode coordinators** (`JobMasterBackgroundAgentWorker.StartCoordinatorAsync`/new `LoadArchiveRunnersAsync`): a Coordinator worker on a `ClusterMode.Archived` cluster (checked via `GetClusterAwareService<IMasterClusterConfigurationService>()`) now starts only heartbeat + `DeleteExpiredGenericRecordsRunner`/`DeleteOldFinalJobsRunner`/`DeleteOldInactiveRecurringSchedulesRunner`/`DeleteOldLogsRunner`, instead of the full `LoadCoordinatorRunnersAsync` set — the bucket-assignment/scheduling runners (`AssignJobsToBucketsRunner`, `ScheduleRecurringJobsRunner`, `WorkerStopCoordinatorRunner`, etc.) would be permanent no-ops on a cluster that can never have buckets or live scheduling (`ClusterMode.Archived` already blocks `JobMasterSchedulerClusterAware.ScheduleAsync`/bucket creation). `Full`-mode coordinators are unaffected — `LoadFullRunnersAsync` still calls the original `LoadCoordinatorRunnersAsync`.

#### Changed
- **`WorkerDefinition.BucketQty` is now a sparse dictionary** (`WorkerDefinition`, `ClusterConfigBuilder`): previously `BucketQty` was always pre-seeded with all five priorities at qty 1. It is now an empty `Dictionary<JobMasterPriority, int>` at construction; `BucketQtyConfig(priority, qty)` only writes the explicitly configured entry. `ClusterConfigBuilder.Finish()` fills in the missing entries: unset priorities default to 1, disabled priorities (from `ClusterDefinition.DisabledPriorities`) are forced to 0. Validation in `Finish()` throws if any disabled priority has an explicit non-zero entry that the user explicitly set via `BucketQtyConfig`.

- **Provider extension methods genericized** (`JobMaster.Postgres`, `JobMaster.MySql`, `JobMaster.SqlServer`, `JobMaster.SqlBase`): `UsePostgresForMaster<T>`, `UseMySqlForMaster<T>`, `UseSqlServerForMaster<T>`, `UseSqlTablePrefixForMaster<T>`, and `DisableAutoProvisionSqlSchema<T>` are now generic with constraint `where T : IBaseClusterConfigSelector<IClusterConfigSelector>`. All call sites keep compiling unchanged — the constraint is satisfied by both `IClusterConfigSelector` and `IBaseClusterConfigSelector<IClusterConfigSelector>`.

- **Fallback bucket now backed by the master DB, not an in-memory queue** (`AssignJobsToBucketsRunner`): previously, when no real bucket was available past `NoBucketFallbackThreshold`, a "fallback bucket" was created using the Coordinator's own `AgentConnectionId`, but its jobs were pushed into a private in-process list (`FallbackBucketJobsOnboardingSource`) — the agent-side `CreateBucketAsync`/`HasJobsAsync`/`DestroyBucketAsync` calls that bucket creation/destruction triggered were therefore dead work against a repository nothing ever read from. Fallback buckets are now created against the reserved `master-fallback-agent-conn` connection and dispatched through the exact same path as regular buckets (`StandardBucketJobsOnboardingSource`, `DispatchJobToBucketAsync`), making fallback jobs durable across a Coordinator restart. `FallbackBucketJobsOnboardingSource` is deleted.

It's expected to show "dead" in the dashboard whenever no fallback bucket is active — a good sign the fallback path isn't being used.
- **Reserved connections exempt from dead-connection cleanup** (`CleanupDeadAgentConnectionsRunner`): `standalone-agent-conn` and `master-fallback-agent-conn` are now excluded from the deletion sweep regardless of heartbeat status, since both are expected to sit dead for long stretches by design.

#### Fixed
- **Orphaned fallback buckets when the owning Coordinator dies** (`AssignedLostBucketsRunner`, `MasterBucketsService`, `DestroyReadyToDeleteBucketsRunner`): if the Coordinator (or Full worker) that created a fallback bucket died, `MarkBucketAsLostRunner` correctly flagged the bucket `Lost`, but `AssignedLostBucketsRunner` could never find a live worker to reassign it to — no real worker can ever own the reserved `master-fallback-agent-conn` connection (see `JobMasterRuntime.PreValidation`) — so the bucket stayed `Lost` forever, along with its agent-side `message_dispatcher`/`bucket_dispatcher` rows, which are only ever cleaned up via the `Draining`/`ReadyToDelete`/`DestroyBucketAsync` path. The affected *jobs* weren't lost (`HeldOnMasterDeadlineTimeoutJobsRunner` reclaims them independently once their deadline passes, regardless of bucket status), but the rows themselves leaked permanently in the master DB. Same bug also reachable via a graceful stop if jobs were still present when `DestroyReadyToDeleteBucketsRunner` next swept the bucket (it would revert it to `Lost` instead of destroying it). Fixed: `AssignedLostBucketsRunner` now sends a `Lost` Fallback bucket straight to `ReadyToDelete` instead of searching for an assignable worker; `MasterBucketsService.DestroyAsync` and `DestroyReadyToDeleteBucketsRunner` now skip the "has jobs" guard for Fallback buckets and force-destroy them regardless — safe because fallback buckets never carry save-pending jobs, only jobs reserved for execution, which recover independently via the deadline runner. Also closed a related gap where a `WorkerDefinition.AgentConnectionName` could be set to the literal reserved string, bypassing the existing `AgentConnections`-only reservation check — `JobMasterRuntime.PreValidation` now rejects that too.

- **Worker could be assigned the reserved standalone connection in a non-standalone cluster** (`JobMasterRuntime.PreValidation`): `JobMasterClusterConnectionConfig.TryGetAgentConnectionConfig`'s lazy resolution for `standalone-agent-conn` has no `IsStandalone` guard — it purely pattern-matches on name and reuses the cluster's own connection string/repo type. A non-standalone cluster's `AddWorker(name, agentConnectionName)` accepts an arbitrary string, and `PreValidation` only checked `AgentConnections` (registered connections) against the reserved name, not `Workers`, so a worker could be pointed at `standalone-agent-conn` by mistake and silently resolve. Fixed with the same pattern already used for `master-fallback-agent-conn`: `PreValidation` now rejects any non-standalone worker whose `AgentConnectionName` equals `standalone-agent-conn`. (The reverse — a standalone-cluster worker pointing elsewhere — was already structurally impossible: `ClusterStandaloneConfigBuilder.AddWorker` has no connection-name parameter at all.)

#### Changed
- **`AgentConnectionId` is nullable for Coordinator workers** (`AgentWorkerModel`, `JobMasterBackgroundAgentWorker`, `IJobMasterBackgroundAgentWorker`): a Coordinator never creates/owns a bucket under its own connection (the fallback bucket it may create uses the separate reserved `master-fallback-agent-conn`, not its own) and is never eligible to claim a bucket for draining (`AssignedLostBucketsRunner` only selects `Drain`/`Full` workers) — so it has no functional need for an agent connection of its own, and now isn't *allowed* to have one. `JobMasterBackgroundAgentWorker.CreateAsync` enforces this as a hard rule: `Mode == Coordinator` with an `AgentConnectionName` configured throws; any other mode without one resolving throws (existing behavior, unchanged). `MasterAgentWorkersService.RegisterWorkerAsync`/`CreateValidatedWorkerAsync`/`StopGracefulWorkerAsync` and the private `AgentWorkerRecord.ToModel` now treat an empty persisted connection id as `null` instead of throwing via the single-string `AgentConnectionId` constructor. `KeepAliveAgentConnectionRunner` is no longer started for Coordinator workers in `JobMasterBackgroundAgentWorker.StartAsync` (previously started unconditionally for every mode). All Full/Execution/Drain-only call sites that read `AgentConnectionId` (bucket runner factories, drain runners, save-pending runners) are guaranteed non-null by the mode split and use `!` accordingly; `AssignedLostBucketsRunner`'s worker-connection match was reordered to filter by `Mode` (Drain/Full) before comparing `AgentConnectionId`, since a Coordinator can now appear in the alive-workers list with a null connection. API surface (`ApiAgentWorker.AgentConnectionId`/`AgentConnectionName`, `WorkersEndpoints` filtering) updated to match.
- **Coordinator connection-name validation moved to `JobMasterRuntime.PreValidation`**: rejecting a Coordinator with an `AgentConnectionName`, and rejecting a non-Coordinator worker whose `AgentConnectionName` doesn't resolve to a registered connection, now both fail fast at bootstrap (before any worker is created) instead of only surfacing per-worker inside `JobMasterBackgroundAgentWorker.CreateAsync`. The non-Coordinator check reports every offending worker by name in one message. `CreateAsync` itself was simplified accordingly — it now just resolves the connection, trusting `PreValidation`'s guarantees, instead of re-validating.
- **`IJobHandler` renamed to `IJobMasterHandler`** (`JobMaster.Abstractions`): brings the primary consumer-implemented extension point in line with the rest of the public surface (`IJobMasterScheduler`, `IJobMasterLogger`, etc.) and reduces collision risk with a very generic name in consuming code. `IJobHandler` is kept as `[Obsolete] interface IJobHandler : IJobMasterHandler` so existing implementations keep compiling without changes; `ClusterConfigBuilder`'s handler auto-registration and `JobsExecutionEngine`'s dispatch both check against `IJobMasterHandler`, so both old- and new-style handlers are picked up identically. - **Reserved agent connection names renamed to a shared `JMReserved-` prefix** (`JobMasterConstants`): `StandaloneAgentConnName` (`standalone-agent-conn` → `JMReserved-standalone`) and `MasterFallbackAgentConnName` (`master-fallback-agent-conn` → `JMReserved-fallback`) now both derive from a new `ReservedAgentConnectionNamePrefix = "JMReserved-"` constant. `IsReservedAgentConnectionName(name)` was simplified from an `ISet<string>` membership check to `name.StartsWith(ReservedAgentConnectionNamePrefix, OrdinalIgnoreCase)`, so any future reserved connection using this prefix is automatically caught without touching this method — and any user-chosen connection name using the prefix is now itself rejected as reserved, closing off future collisions. Deliberately keyed on `BucketType.Fallback`, not "does this bucket use a reserved connection" — standalone buckets also use a reserved connection (`JMReserved-standalone`) but are ordinary buckets that must still wait for their jobs to drain before destruction; only the fallback-bucket mechanism is exempt from the guard. No behavior change.

#### Changed
- **Fallback bucket priority selection now respects `DisablePriority`** (`AssignJobsToBucketsRunner.EnsureFallbackBucketAsync`): both `DisablePriority` and the fallback bucket's initial hardcoded `JobMasterPriority.Critical` were introduced in this same release, so this isn't a regression fix — it's the fallback path needing to account for the new `ClusterDefinition.DisabledPriorities`/`JobMasterClusterConnectionConfig.IsPriorityDisabled` check once both landed. Bucket creation for the fallback path bypasses normal `BucketQty` sizing entirely, so nothing downstream would otherwise reject an assignment to a disabled priority. Implemented with a `FallbackPriorityPreference` array (`Critical`, `High`, `Medium`) and a new `ResolveFallbackPriority()` that returns the first non-disabled entry; `Medium` can never be disabled (enforced in `ClusterDefinition.DisablePriority`), so this is guaranteed to resolve. Both the bucket's `CreateAsync` call and `fallBackRunner.DefineBucketId` use the resolved priority instead of a hardcoded literal. Covered by two new tests in `AssignJobsToBucketsRunnerTests` (`WhenCriticalIsDisabled_FallsBackToHighPriority`, `WhenCriticalAndHighAreDisabled_FallsBackToMediumPriority`).

- **`ConnectionOptionsStrategyFactory.Discover()` unguarded reflection scan** (`ConnectionOptionsStrategyFactory`): unlike the near-identical handler-type scan added in `JobMasterRuntime.PreValidation` in this same release, `Discover()`'s `a.GetTypes()` call had no try/catch. Since `Strategies` is a `static readonly` field, a `ReflectionTypeLoadException` thrown by any unrelated loaded assembly on first use (i.e. the first `ConfigFromJson` call with a `connectionOptions` dictionary) would permanently poison the type — every subsequent `Create(...)` call for the rest of the process's lifetime immediately rethrows `TypeInitializationException` without ever retrying `Discover()`, per normal CLR static-initialization semantics. Fixed by wrapping the `GetTypes()` call the same way `JobMasterRuntime.cs` already does (`try { return a.GetTypes(); } catch { return Array.Empty<Type>(); } }`).
- **`ProtectConnectionChanges` was never persisted** (`MasterAgentConnectionService.SaveConnectionAsync`): the `protectChanges` parameter — correctly passed in from `JobMasterRuntime` as `agentDefinition.ProtectConnectionChanges` — was never assigned to the persisted `AgentConnectionRecord`, on creation or update. So no connection could ever actually become "protected" in the database regardless of configuration; `ProtectConnectionChanges` was always `false`. Fixed: it's now written on every save, so protection can also be toggled by changing config and restarting.
- **Protected connections could never be cleaned up, even once truly abandoned** (`CleanupDeadAgentConnectionsRunner`): previously `ProtectConnectionChanges == true` connections were unconditionally excluded from the deletion sweep forever. `ProtectConnectionChanges` is about detecting a silently-changed underlying connection at bootstrap (the fingerprint check in `JobMasterRuntime`) — it's unrelated to deletion timing, so protected and unprotected connections now share the same dead threshold (`DeleteAgentConnectionThreshold`, 30 minutes — renamed from `DeadAgentConnectionThreshold` since it isn't about detecting "dead," `IsAlive()`'s 45s window already does that, it's specifically how long a dead connection is left alone before being deleted); `SafeDeleteConnectionAsync` still only deletes once the connection has no buckets left, so a connection is never removed out from under work that still needs to drain. The existing early-warning critical log (dead + protected + still has buckets) is unchanged. `CleanupDeadAgentConnectionsRunner` was also fully dead code until now — nothing instantiated it in any `Load*RunnersAsync` method — so it's now started in `LoadCoordinatorRunnersAsync`.
- **Agent connection save/delete race condition**: `MasterAgentConnectionService.SaveConnectionAsync` (fingerprint creation/update) and `SafeDeleteConnectionAsync` now both acquire the same per-connection distributed lock (`JobMasterLockKeys.AgentConnectionLock`) before touching a connection's record, so a concurrent save and delete for the same connection can no longer race. `SaveConnectionAsync` retries briefly (up to ~2s) to ride out concurrent bootstrap from multiple processes registering the same shared connection; `SafeDeleteConnectionAsync` just skips this cycle if the lock is held, since the cleanup runner retries every 5 minutes anyway.
- **`(LastHeartbeatAt ?? FingerprintCreatedAt)` assumed the heartbeat, when present, is always more recent than the fingerprint-creation time** (`AgentConnectionModel`, `CleanupDeadAgentConnectionsRunner`): not true after a connection is deleted and later recreated — the heartbeat log entry from the previous incarnation is never cleared, so a stale old heartbeat could outlive a brand-new `AgentConnectionRecord` and make a just-recreated connection look immediately dead/eligible for deletion. Fixed by resolving `AgentConnectionModel.LastHeartbeatAt` once, at fetch time (`MasterAgentConnectionService.ToModel`), as whichever of the raw heartbeat and `FingerprintCreatedAt` is more recent — the property is now non-nullable `DateTime`, and `IsAlive()`/`CleanupDeadAgentConnectionsRunner`'s dead-threshold check both just read it directly instead of each re-deriving the same fallback.
- **`IsAlive` standardized across `AgentConnectionModel`, `AgentWorkerModel`, and `HostModel`**: `AgentWorkerModel.IsAlive` was a settable `bool` property (populated by `MasterAgentWorkersService.ToModel` from a separately-computed `isAlive` bool) instead of a computed method like the other two models — and, same as the connection bug above, its `LastHeartbeat` could go stale-relative-to-recreation if a worker/host record was deleted and recreated without a matching heartbeat-log cleanup. Fixed by applying the exact same pattern used for `AgentConnectionModel`: `AgentWorkerModel.IsAlive`/`HostModel.IsAlive` are threshold comparisons over a non-nullable `LastHeartbeat`, resolved once at fetch time as `Max(rawHeartbeat, CreatedAt)` (`MasterAgentWorkersService.ToModel`, `MasterHostService.ToHostModel`). All three models' thresholds are also unified into one new constant, `JobMasterConstants.ResourceAliveThreshold` (30s heartbeat threshold + `ClockSkewPadding` = 45s), replacing three previously-inconsistent inline windows: `AgentConnectionModel` (90s), `AgentWorkerModel` (30s, no clock-skew padding), `HostModel` (45s, already correct but hardcoded). Every call site of the now-removed `AgentWorkerModel.IsAlive` property (`WorkersEndpoints`, `ApiAgentWorker.FromDomain`, `CleanupDeadWorkerRunner`, `MarkBucketAsLostRunner`) updated to call `IsAlive()`.
- **Agent-side fingerprint generation wasn't atomic under concurrent bootstrap** (`SqlAgentFingerprintResolver`): when a brand-new agent connection is bootstrapped by two processes at the same time (the exact scenario `MasterAgentConnectionService.SaveConnectionAsync`'s lock-retry loop was built to tolerate), each process independently generated its own random fingerprint GUID; the insert path was `INSERT ... WHERE NOT EXISTS (...)` followed by an *unconditional* `UPDATE` that always overwrote the row with the caller's own locally-generated value — regardless of whether that caller's `INSERT` actually won the race. So the "loser" process could return a fingerprint value that no longer matched what was actually persisted in the agent-side table, which would then surface as a false-positive "connection fingerprint has changed" failure on the next restart (fatal for any connection with `ProtectConnectionChanges = true`). Fixed: the resolver now does a plain `INSERT` relying on the existing `(cluster_id, agent_connection_id)` primary key for atomicity, catches the provider-specific duplicate-key exception, and on conflict re-reads and returns whatever the actual winner persisted instead of trusting its own local value. Matches the atomicity the NATS JetStream resolver already had (`CreateAsync` + re-read-on-conflict).
- **`IKnownExceptionIdentifier` silently assumed the cluster's own (master) repo type, breaking agent-side exception classification** (`JobMaster.Sdk.Abstractions.Exceptions`): the original `IKnownExceptionIdentifier.Identify(Exception ex)` resolved its provider strategy from `ClusterConnConfig.RepositoryTypeId` — i.e. the *cluster's own master* repo type — which is correct for every existing master-side caller (`MasterJobsService`, `MasterAgentConnectionService`, `SqlMasterJobsRepository` family, etc.) but silently wrong for the new `SqlAgentFingerprintResolver` fix above: an agent connection's repo type can differ from the cluster's master repo type, so an agent-side duplicate-key exception could be handed to the *wrong* provider's strategy and misclassified as unrecognized, propagating uncaught instead of being handled. The same master-repo-type assumption also affected `JobMasterRunner`'s generic tick-failure weighting (`CalcFailureWeight`), which can classify exceptions from any agent connection a runner happens to touch. Compounding both, `IKnownExceptionIdentifierStrategy` implementations were only ever registered in each provider's `RegisterForMaster` — never `RegisterForAgent` — so even a correct repo-type lookup could find nothing registered for an agent-only repo type. Fixed by giving `IKnownExceptionIdentifier` (impl: `KnownExceptionIdentifier`) two methods instead of introducing a second interface: `Identify(string repoType, Exception ex)` for callers that know exactly which repo type threw (`SqlAgentFingerprintResolver` with its own `AgentRepoTypeId`, `SqlMasterJobsRepository.IsDupeViolation` with `ClusterConnConfig.RepositoryTypeId`), and an `Identify(Exception ex)` overload for callers with no single connection in scope (`JobMasterRunner`, `RetryDeadlockPolicy`) that tries every strategy registered for the cluster and returns the first match — safe because the raw provider exception types each strategy pattern-matches on are mutually exclusive CLR types, so there's no real ambiguity to resolve by repo type, and cheap since a cluster only ever registers a handful of strategies. `IKnownExceptionIdentifierStrategy` is now also registered in `RegisterForAgent` for SqlServer/Postgres/MySql, so an agent-only repo type has its strategy available; `KnownExceptionIdentifier`'s strategy dictionary construction was made dedupe-safe (`GroupBy` + take first) since a repo type used for both the master and an agent connection now legitimately registers its strategy twice.
- **`ClusterDefinition.IsStandalone` changed from `bool` to `bool?`** (`ClusterDefinition`, `ClusterConfigBuilder`, `JobMasterRuntime`): when `IsStandalone` was a non-nullable `bool`, its default value of `false` was indistinguishable from a user explicitly setting `IsStandalone = false`. This meant that for clusters configured via `ConfigFromJson` (which never calls `ClusterStandaloneConfigBuilder`, so `ClusterDefinition.IsStandalone` was never set to `true` in code), the runtime merged the code-level `false` over the database-stored `true`, effectively stripping standalone mode on every restart. Now nullable; `JobMasterRuntime.StartAsync` resolves `var isStandalone = clusterDefinition.IsStandalone ?? modelToSave.IsStandalone` and uses `isStandalone` throughout. All boolean-guard comparisons updated to `clusterDefinition.IsStandalone == true` / `clusterDefinition.IsStandalone != true` pattern to handle the nullable correctly.

- **`NotifyChanges` called after the write instead of before, in 5 places** (`MasterAgentConnectionService.SaveConnectionAsync`/`SafeDeleteConnectionAsync`, `MasterHostService.RegisterNewHostAsync`/`UpdateStatsAsync`/`DeleteHostsAsync`): `IMasterChangesSentinelService.NotifyChanges` bumps a sentinel's `LastUpdate` timestamp (to `UtcNow + SentinelNotifyPadding`) so `SentinelCachedReader`-backed caches on other processes know to invalidate and re-fetch. Calling it *after* the DB write means any failure between the write and the notify call (an exception thrown by a later step, the process dying, etc.) leaves the write durably committed but the sentinel never bumped — every cached reader keeps serving pre-write data until its entry's own TTL naturally expires (`durationToExpire`, typically minutes), not just until the next poll. Calling it *before* the write is safe by construction: a failure between notify and write just costs a wasted re-fetch of still-unchanged data, never a permanently stale cache; and `SentinelNotifyPadding`'s forward padding exists specifically to cover the case where a concurrent reader's fetch races into the gap and reads pre-write data — that reader's freshly-cached entry still has `CreatedAt` earlier than the padded `LastUpdate`, so it's correctly re-invalidated on the next check instead of being trusted for the full TTL. `MasterAgentWorkersService` and `MasterBucketService` already notified before writing in every method; `MasterClusterConfigurationService.Save` was already correct too — only the 5 sites above were reordered.

#### Fixed
- **Message-size enforcement consolidated onto a single, correct checkpoint** (`JobMasterSchedulerClusterAware`, `AgentJobsDispatcherRepository`, `JobMasterRawMessage`): the size guard was previously duplicated and, on one path, missing entirely. `EnforceMasterStoreSizeLimit` (now `EnforceSizeLimit`) was called only inside the "held on master" branch of each scheduling method — the bypass branch (a bucket is available at schedule time) called `agentJobsDispatcherService.AddSavePendingJobAsync`/`AddSavePendingRecur(Async)` with no size check of its own in the scheduler at all, relying entirely on `AgentJobsDispatcherRepository`'s `EnforceDispatchSizeLimit`, called from inside `PushSavePendingJob(Async)`/`PushForProcessing(Async)`/`PushForSaving(Async)`/`BulkPushSavePendingJobAsync`. For a job that started out `HeldOnMaster` and was later picked up by the Coordinator and dispatched into a bucket, this meant the same job got checked twice, at two different points in its lifecycle, against data (`MsgData`/`Metadata`) that never changes between those two points. Consolidated: `EnforceSizeLimit` now runs once, unconditionally, at the top of every scheduling method (`ScheduleAsync(JobRawModel)`, `BulkScheduleAsync`, `Schedule(RecurringScheduleRawModel)`, `Schedule(JobRawModel)`, `ScheduleAsync(RecurringScheduleRawModel)`) — before the master-vs-bypass branch, so both paths are covered by one check. `EnforceDispatchSizeLimit` and all 6 of its call sites were removed from `AgentJobsDispatcherRepository` entirely.
- **`CalcEstimateByteSize` fully re-serialized the whole record just to measure it, and silently dropped `Metadata`'s size when fixed naively** (`JobMasterRawMessage`, `JobMasterSchedulerClusterAware`): the two `EnforceMasterStoreSizeLimit` overloads called `JobMasterRawMessage.CalcEstimateByteSize<T>(job, ...)` / `(recur, ...)` — the generic overload, which called `InternalJobMasterSerializer.Serialize<T>(payload)` to fully JSON-serialize the entire `JobRawModel`/`RecurringScheduleRawModel` object graph purely to call `.GetByteCount()` on the result and discard it; the serialized string was never otherwise used. Fixed by calling the string-based overload directly with `job.MsgData`/`recur.MsgData` — no serialization at all, just `UTF8.GetByteCount` on strings that already exist on the model. Because the old generic-overload path serialized the *whole* object, it had been accidentally capturing `Metadata`'s byte contribution as a side effect; switching to `MsgData` alone would have silently under-counted the estimate and weakened the size guard. `CalcEstimateByteSize` was given a `metadata` parameter (appended as the last parameter, default `null`, specifically so the generic overload's existing positional call didn't need to change) so `Metadata`'s size is now measured explicitly via a second `UTF8.GetByteCount` call, only when non-empty.
- **`IMasterClusterConfigurationService` was a dependency of the repository layer** (`AgentJobsDispatcherRepository` and its four concrete subclasses — `SqlServerJobsDispatcherRepository`, `PostgresJobsDispatcherRepository`, `MySqlJobsDispatcherRepository`, `NatsJetStreamJobsDispatcherRepository`): the only consumer of this dependency was `EnforceDispatchSizeLimit`, removed above — a repository reaching into a service-layer interface for `MaxMessageByteSize` was a layering inversion in its own right, independent of the duplicate-check bug. Removed the field and constructor parameter from the base class and all four subclasses; DI resolves these types by type through `AddKeyedTransient`/`GetRequiredKeyedService`, so no registration/factory changes were needed. `Tests/JobMaster.UnitTests/Repositories/AgentJobsDispatcherRepositoryTests.cs` was deleted — its two tests existed solely to exercise `EnforceDispatchSizeLimit` via reflection, which no longer exists.
- **`BulkScheduleAsync` could partially commit a batch before failing size validation** (`JobMasterSchedulerClusterAware.BulkScheduleAsync`): `EnforceSizeLimit` was called inside the same loop that also called `masterJobsService.AddAsync` for jobs held on master. An oversized job partway through a batch threw only after every preceding job in that same batch had already been durably written — the caller's exception gave no indication that part of the batch had committed, so a naive "catch and retry the whole list" pattern would duplicate the jobs that already succeeded. Fixed by validating every job's size in its own pass, with no side effects, before the bucket-assignment/persistence loop runs — one oversized job anywhere in the batch now fails the entire call before anything is written or dispatched.

- **`MarkBucketAsLostIfNotDrainingAsync` TOCTOU race could mark a bucket `Lost` after it had already moved past the exempt window** (`WorkerClusterOperations`): the status check read `masterBucketsService.Get(bucketId, BucketFastAllowDiscrepancy)` — a cached, possibly-stale snapshot — and, if the cached status wasn't `Draining`/`ReadyToDrain`/`Lost`, called `MarkBucketAsLostAsync` unconditionally with no lock and no re-check. #### Fixed
- **`MarkBucketAsLostRunner`'s periodic sweep silently failed to mark orphaned buckets `Lost` via a stale cached read** (`WorkerClusterOperations.MarkBucketAsLostAsync(string bucketId)`): this overload re-fetched the bucket via `masterBucketsService.Get(bucketId, BucketFastAllowDiscrepancy)` — a cached read — before mutating and writing it back, instead of a fresh uncached read like its sibling `MarkBucketAsLostIfNotDrainingAsync` (fixed earlier this same release, see above). `MarkBucketAsLostRunner` calls this overload once per bucket it's already determined needs marking `Lost` (via its own fresh `QueryAllNoCacheAsync()` scan), so the redundant cached re-fetch served no purpose beyond risking a stale/inconsistent read on the write path. Found live building `DrainModeTest` (`Tests/JobMaster.ScenarioTests/Scenarios/DrainModeTest/PostgresDist`), a new scenario that isolates each `AgentWorkerMode` into its own container and forces a drain under real in-flight load (5000 jobs) — a shape none of the existing `ScheduleTest` drain coverage exercises, since that suite only ever drains an already-idle cluster. Fixed by having `MarkBucketAsLostRunner` pass the already-fresh `BucketModel` it already holds directly to `MarkBucketAsLostAsync(BucketModel)` (no re-fetch at all — matches the pattern `WorkerStopCoordinatorRunner` already used), and by fixing the `string bucketId` overload itself (still needed by `NatsJetStreamRunnerBase`, which only has a bucket ID on hand) to use a new dedicated primitive, `IMasterBucketsService.GetNoCacheAsync(string bucketId)`, instead of an awkward single-item `QueryAsync(new MasterBucketQueryCriteria { BucketIds = [...] })` workaround.
- **`DrainRunnersCoordinator` contended a cluster-wide lock it never needed at all** (`JobMasterLockKeys.BucketRunnerLock()`): not a correctness bug — no bucket was ever left permanently stuck — but `MarkBucketAsLostRunner`, `AssignedLostBucketsRunner`, `DrainRunnersCoordinator`, and `DestroyReadyToDeleteBucketsRunner` all serialized against each other through one global lock key, and `DrainRunnersCoordinator` runs every 10 seconds *per worker* — by far the highest-frequency contender (3 drainers × 6/min = 18 lock attempts/min from this runner alone, before counting the other three). Its own bucket queries (`CreateDrainRunners`/`RecoverDrainRunnersAsync`) are already filtered to `AgentWorkerId == BackgroundAgentWorker.AgentWorkerId`, so two different drainers' ticks never touch overlapping state, and actual mutations already go through a separate per-bucket lock (`BucketLock(bucket.Id)`) — the global lock added contention with no correctness benefit for this specific runner. Under `DrainModeTest`'s 3-drainer topology at load this made the drain-to-destroy timeline for a given connection noticeably slow and uneven (one connection could finish in minutes while another took most of the observed window), and pushed one run past a 40-minute test timeout. Investigated further: every `JobMasterRunner` subclass with `useSemaphore: true` (which `DrainRunnersCoordinator` already is) already serializes against every other such runner *on the same worker process* via `BackgroundAgentWorker.MainSemaphoreSlim` — so no cross-runner distributed lock was needed here at all, not even a worker-scoped one. Fixed by removing `DrainRunnersCoordinator.OnTickAsync`'s lock acquisition entirely (not narrowing its scope) — different workers' coordinator ticks now run fully in parallel, with within-worker serialization still guaranteed by the existing semaphore. `AssignedLostBucketsRunner` and `MarkBucketAsLostRunner` were left on the shared global lock (both genuinely scan cluster-wide, not per-worker, so de-contending them isn't the same obviously-safe change) — worth a follow-up look if drain throughput under multi-worker load is still a concern.

#### Fixed
- **`AssignJobsToBucketsRunner`'s dispatch-batch parallelism was a fixed constant regardless of cluster size** (`AssignJobsToBucketsRunner.OnTickAsync`): the `ParallelOptions.MaxDegreeOfParallelism` passed to `JobMasterParallelUtil.ForEachAsync` for dispatching an assigned batch was hardcoded to `5`, so the Coordinator's per-tick dispatch throughput was capped at that value no matter how many distinct buckets/workers the batch actually targeted — adding execution workers to a cluster did nothing to raise the ceiling. Found live while benchmarking JobMaster against Quartz.NET/Hangfire under sustained load (`Benchmarks/`): worker CPU sat at single digits with a large `WAITING`-bucket backlog visibly building, ruling out a resource limit. Fixed: `maxParallelism` is now `bucketAssignments.Values.Select(b => b.Id).Distinct().Count()`, floored at the old fixed value (`5`, so small batches/clusters aren't regressed) and capped at `JobMasterConstants.MaxBatchSizeForBulkOperation` (`50`, the same constant already used for the bulk-update batch size immediately above it in the same method) so parallelism doesn't grow unbounded with an unusually wide batch.
- **`AgentComponentFactory`'s per-connection repository/fingerprint-resolver cache was a plain, non-thread-safe `Dictionary`** (`AgentComponentFactory.repositoriesByAgentConnectionId`/`fingerprintResolversByAgentConnectionId`): both lazy-init caches used `Dictionary<string, T>` with a check-then-add pattern (`TryGetValue` miss → construct → assign) with no synchronization at all. Harmless as long as a process only ever resolves one agent connection at a time, which is why this was latent — it only surfaces once a process genuinely reaches multiple agent connections concurrently (a Coordinator dispatching to several executors' connections at once is the common real case). Found live in the same benchmark session as the dispatch-parallelism fix above, once that fix let the Coordinator's dispatch rate actually scale with worker count and hit true concurrent multi-connection resolution for the first time in this codebase's history. Fixed: both fields are now `ConcurrentDictionary<string, T>`, populated via `GetOrAdd` with the same construction lambda, giving the standard exactly-once-construction guarantee under concurrent first use.
- **`RecurringSchedulePlanner` drifted a schedule's effective anchor whenever its interval exceeded the cluster's `TransientThreshold`** (`RecurringSchedulePlanner.ScheduleNextJobsAsync`/`PlanNextDates`): `ScheduleNextJobsAsync`'s empty-`nextDates` branch set `scheduleRawModel.LastPlanCoverageUntil = checkTime`, where `checkTime` fell back to `planningHorizonUsed` (`DateTime.UtcNow + horizon` at that specific tick) whenever `PlanNextDates` found no occurrence within the horizon. `LastPlanCoverageUntil` doubles as the `baseDateTime` cursor fed into `PlanNextDates`/`GetNextOccurrence` on the *next* attempt, so this planning-window boundary — an arbitrary tick-time with no relationship to the recurrence's actual cadence — silently replaced the schedule's true anchor (`StartAfter ?? CreatedAt`) as the reference point every future occurrence was computed from. Only reachable when a schedule's own interval exceeds the cluster's horizon, which under normal `TransientThreshold` configuration never happens — but `NatsJetStreamConstants.MaxThreshold` unconditionally caps `TransientThreshold` at 5 minutes for any NATS JetStream cluster, so any recurring schedule with an interval longer than 5 minutes on such a cluster hit this every time. Found live investigating an intermittent `Tests/JobMaster.ScenarioTests` `RecurringScheduleTest.PostgresNats` timing failure (a 6-minute-interval schedule against NATS's 5-minute cap) — confirmed via direct queries against the running scenario's own Postgres master DB mid-test, correlating `jm_recurring_schedule.last_plan_coverage_until`/`jm_job.scheduled_at` timestamps against the actual `jm_log` `WARN` entries the empty-branch path emits.

  Two intermediate fixes were tried and superseded before landing on the final design, each surfacing a real problem with the previous one: (1) simply not advancing `LastPlanCoverageUntil` on an empty pass fixed the drift but reintroduced unbounded re-probing — `ScheduleRecurringJobsRunner`'s own `ScanPlanner.ComputeScanPlanHalfWindow` interval only backs off when it sees zero backlog, so a schedule whose interval genuinely exceeds the horizon (e.g. "every year") would look due on literally every tick, forever, since the watermark never moved; (2) having `PlanNextDates` report the true next occurrence separately for throttling purposes (advancing the watermark to `nextOccurrence - horizon` without materializing/dispatching the job early) fixed that too, but added a second return value and caller-side "materialize vs. throttle" branching whose only reason to exist was avoiding early dispatch to transports with bounded pending-message capacity (NATS JetStream's `MaxAckPending`).

  Final design, per explicit call to always dispatch a recurring job as soon as its next occurrence is known regardless of how far out it is (a cancelled schedule just cancels its already-materialized job along with it, same as any other): `PlanNextDates` now applies one rule — always return at least one occurrence, even when it's beyond the horizon, *unless* the horizon was clamped by the schedule's own explicit `EndBefore` rather than by the cluster horizon (tracked via a new `stopAtIsExplicitEnd` local; materializing a job past a declared `EndBefore` would be wrong, so that case correctly stays empty and lets the existing `HasEnded` check mark the schedule `Completed`). The generation loop's `for` condition no longer gates on `cursor <= stopAt` — needed so at least one `GetNextOccurrence` call always happens even when `baseDateTime` itself already starts beyond the horizon, not just when the recurrence's interval exceeds it; termination is now entirely up to the loop body's own breaks (occurrence exhausted, occurrence beyond `stopAt`, progress guard), still bounded by `MaxOccurrencesPerRun`. `PlanNextDates`' return signature is unchanged (3-tuple) — the two-return-value design from the intermediate fix was fully reverted. `ScheduleNextJobsAsync`'s empty-`nextDates` branch (now reachable only for a genuinely-exhausted recurrence or an `EndBefore` that clamps the horizon while still itself being in the future) unconditionally sets `LastPlanCoverageUntil = checkTime` before checking `HasEnded`, instead of only in the "ended" sub-branch — simpler, and stable in the `EndBefore`-clamped case (pins the watermark at `EndBefore` itself, since `GetNextOccurrence(EndBefore)` keeps landing beyond the still-clamped horizon on every subsequent attempt, until `EndBefore` actually passes and the unconditional check already at the top of `ScheduleNextJobsAsync` converts the schedule to `Completed`).

  `Tests/JobMaster.UnitTests/Services/RecurringSchedulePlannerTests.cs`: the two existing "beyond horizon" tests (`PlanNextDates_WithBaseDateTimeBeyondHorizon_...`, `PlanNextDates_WithNaturalCron_BaseDateTimeBeyondHorizon_...`) renamed from `...ShouldReturnEmpty` to `...ShouldReturnSingleOccurrenceAnyway` and their assertions inverted to match; added `PlanNextDates_WithIntervalExceedingHorizon_ShouldReturnSingleOccurrenceAnyway` (a 365-day `TimeSpanInterval` against a 5-minute horizon, directly modeling the motivating scenario) and `PlanNextDates_WithIntervalExceedingHorizon_AndExplicitEndBefore_ShouldReturnEmpty` (locks in the one case that must still return empty).

#### Changed
- **Jobs/RecurringSchedules ordinary reads no longer `LEFT JOIN` the generic-record metadata tables** (`JobPersistenceRecord`/`RecurringSchedulePersistenceRecord`, `SqlMasterJobsRepository`/`SqlMasterRecurringSchedulesRepository` and provider overrides, `MasterTableCreatorScripts`): a new nullable `MetadataJson` column stores the already-serialized metadata directly on the `job`/`recurring_schedule` row (populated via `KeyValueBagUtil.Serialize`, below), so `Get`/acquire/`Query` select it directly with no join. The generic-record entry/value tables remain the source of truth and are still written on every save, and are still joined for `MetadataFilters`-based querying specifically (`needsMetadataJoin`) — this only removes the join from reads that don't filter by metadata. Purely an internal read-path optimization, no behavior change for callers; not listed in `ChangeLog.md`.

- **`KeyValueBagUtil`** (new, `JobMaster.Sdk.Abstractions.Jobs`): Metadata and MsgData are both backed by the same underlying `KeyValueBag`, so `JobConvertUtil`/`RecurringScheduleConvertUtil` each independently inlined the same null-check-then-deserialize boilerplate for both, four times over. Consolidated into `Serialize(IWritableMetadata?)`, `Serialize(IWriteableMessageData?)`, `DeserializeMetadata(string?) → IWritableMetadata`, `DeserializeMessageData(string?) → IWriteableMessageData`; both converters now call through this instead of touching `InternalJobMasterSerializer`/`Metadata`/`MessageData` directly. New `DateTimeExtensions.AsUtc()` (`DateTime`/`DateTime?` overloads) similarly replaces near-identical local `Utc`/`UtcN` helper functions that were duplicated inside both converters' `FromPersistence` methods. Covered by new `KeyValueBagUtilTests.cs`, round-tripping every supported primitive type for both Metadata and MsgData, plus a documented non-roundtrip case for `byte[]` on MsgData (see below).

- **`byte[]` and enum support removed from `IReadableMetadata`/`IWritableMetadata`/`Metadata`** (`GetByteArrayValue`/`TryGetByteArrayValue`/`SetByteArrayValue`, `GetEnumValue<TEnum>`/`TryGetEnumValue<TEnum>`/`SetEnumValue<TEnum>` all deleted): both round-trip ambiguously through the JSON-based heuristic deserializer Metadata now shares with MsgData via `KeyValueBagUtil` — a `byte[]` comes back as an indistinguishable base64 string, and an enum comes back as a plain number with nothing to reconstruct the original type against, confirmed via a `KeyValueBagUtilTests` case that documents the failure rather than hiding it. Both remain supported on `MessageData`/`IWriteableMessageData`/`IReadableMessageData` and the underlying `KeyValueBag` unchanged — removed from Metadata specifically since it's the type most exposed to querying/filtering, where a silently-wrong round trip is more likely to bite than on MsgData's typical write-once/read-once usage.

- **`KeyValueBag.SetUtcDateTimeValue` renamed to `SetDateTimeValue`** (`IWritableMetadata` too): previously forced the incoming value to UTC (`.ToUniversalTime()`) before storing; now stores whatever `DateTime.Kind` the caller passed in, unchanged. This was papering over the serializer Kind bug fixed below — forcing UTC at the write API masked what should have been fixed at the read/deserialize layer.

- **`IsReady` removed from the generic-record system entirely** (`SqlGenericRecordEntry`/`SqlGenericRecordEntryLinearDto`, `GenericRecordSqlUtil`, `MasterTableCreatorScripts`): the flag existed to stop a reader from seeing an "entry" row before its "value" rows committed, which was only reachable under the old dirty/uncommitted-read `ReadIsolationLevel` concept already removed earlier this release (see "All database reads now use READ COMMITTED" above). Under READ COMMITTED, with entry+value writes inside one transaction, no reader can observe a partial write regardless of this flag, making it dead weight. Removed the `is_ready` column (and its default/index-list inclusion — index names keep their existing `_ready` substring for continuity even though the column itself is gone), the `WHERE IsReady = true` filter previously appended to every generic-record read, and `GenericRecordSqlUtil.BuildSetReadySql`/`BuildSetReadyMultipleSql` — the latter's removal collapses `SqlMasterGenericRecordRepository.BulkInsertAsync` from two round trips (insert, then a follow-up "set ready" pass) down to one. Purely internal/DB-schema-only, not listed in `ChangeLog.md`.

- **`AssignJobsToBucketsRunner.OnTickAsync` split into five named step methods** (`ProbeDiagnosticAsync` → `AcquireJobsAsync` → `AssignJobsToBucketsInMemoryAsync` → `BulkUpdateJobsOnMasterAsync` → `DispatchJobsToBucketsAsync`, ordered above the runner's other private methods): previously one long method covering the whole tick. Each step has its own `Stopwatch`, feeding one combined debug log line (`acquireMs=... assignMs=... bulkUpdateMs=... dispatchMs=...`) for tick-level observability. Readability/structure only, no behavior change, not listed in `ChangeLog.md`.

- **Fallback bucket assignment folded into the normal per-tick dispatch flow** (`AssignJobsToBucketsRunner`, `IWorkerClusterOperations`, `WorkerClusterOperations`): `HandleJobFallbackAssignmentAsync` now just assigns the resolved fallback `BucketModel` to the job in-memory (`job.AssignToBucket(bucket)`) once `NoBucketFallbackThreshold` elapses — the same as an ordinary bucket assignment — instead of dispatching it through a separate dedicated call, so it now rides through the same bulk-update-then-dispatch steps as every other job in the tick. This made the single-job `IWorkerClusterOperations.DispatchJobToBucketAsync` fully redundant with `BulkDispatchJobsToBucketAsync` (confirmed zero remaining callers), so it was removed from the interface and `WorkerClusterOperations` entirely. `HandleJobBucketAssignmentResult` (internal enum) simplified from `{Success, FallbackAssignment, Failed, Canceled}` to `{Success, Failed, Canceled}` to match. `BulkJobUpdateRequest.ReleasePartitionLock(IList<Guid>)` (bulk, clearing only `PartitionLockId`/`PartitionLockExpiresAt`) replaces the deleted single-row `IMasterJobsRepository.ReleasePartitionLock(Guid)`. Internal restructuring only — dispatch behavior for fallback jobs is unchanged from the caller's perspective, not listed in `ChangeLog.md`.

- **New bulk "for processing" dispatch path, mirroring the existing bulk save-pending one** (`IAgentJobsDispatcherRepository.BulkPushForProcessingAsync`/`AgentJobsDispatcherRepository`, `IAgentJobsDispatcherService.BulkAddForProcessingAsync`/`AgentJobsDispatcherService`): previously only single-job `PushForProcessing(Async)` existed for handing an already-assigned job straight to its bucket's execution transport, so `WorkerClusterOperations.BulkDispatchJobsToBucketAsync` issued one agent-side write per job even though the bulk save-pending path already had a batched equivalent. `BulkPushForProcessingAsync` builds one `(payload, referenceTime, correlationId)` tuple per job and hands the whole batch to `processingRepository.BulkPushMessageAsync` in one call; `WorkerClusterOperations` now collects everything that isn't handled by the same-worker in-memory short-circuit and sends it through a single `BulkAddForProcessingAsync` call per bucket instead of N individual dispatch writes. Also cleaned up in the same pass: `BulkAddSavePendingJobAsync`'s per-bucket grouping/partitioning logic moved out of `AgentJobsDispatcherService` and into its callers (`JobMasterSchedulerClusterAware.BulkScheduleAsync` now groups by `BucketId` and partitions before calling), so the method itself just takes an already-grouped `(agentConnectionId, bucketId, jobs)` and no longer needs to infer them from the first job in the list.

- **`BulkUpdateAsync` gained a `useAcquireThrottler` option to serialize it against the acquire pipeline** (`IMasterJobsService.BulkUpdateAsync` — both overloads, `MasterJobsService`): the Coordinator's OnMaster→InBucket bulk update (`AssignJobsToBucketsRunner`'s bulk-update step) previously ran through the same general-purpose `operationThrottler` as every other write, which has much higher concurrency than the dedicated `acquireOperationThrottler` (1 op / 5000ms per cluster) that already serializes `AcquireAndFetchAsync` across every coordinator instance in the cluster. That let one coordinator's bulk update run fully concurrently against another coordinator's acquire, confirmed via benchmark to matter for throughput. `AssignJobsToBucketsRunner` now passes `useAcquireThrottler: true` on this specific call (and on the `HeldOnMaster` dispatch-failure recovery path, above) to route it through the same per-cluster throttler as acquire instead; other callers (e.g. execution workers persisting completion status) default to `false` and stay on the general throttler, since they have no reason to be serialized with the acquire pipeline.

- **Dispatch parallelism now scales per agent connection as well as per bucket** (`AssignJobsToBucketsRunner.DispatchJobsToBucketsAsync`, new `JobMasterConstants.MaxParallelAgentConnectionDispatch` = 10 / `MaxParallelBucketDispatchPerAgentConnection` = 5): dispatch now groups the tick's assigned jobs by bucket, then by the bucket's `AgentConnectionId`, fanning out with two nested parallelism levels instead of the single flat cap from the earlier dispatch-parallelism fix this release. A partition that fails to dispatch is now recovered via `masterJobsService.BulkUpdateAsync(BulkJobUpdateRequest.HeldOnMaster(...), useAcquireThrottler: true)` instead of aborting the tick's remaining dispatch work.

- **`ClusterJsonConfig.DebugJsonlFilePath`**: when set, mirrors every log entry — including Debug-level entries that are never persisted to the database — to a JSONL file (`ClusterConfigBuilder.Build`). #### Fixed
- **`InternalJobMasterSerializer` relabeled every deserialized `DateTime` to UTC, discarding whatever Kind `RoundtripKind` had actually parsed**: deserialization forced `new DateTime(dto.Ticks, DateTimeKind.Utc)` unconditionally, silently shifting the represented instant for any value that had round-tripped as `Local`/`Unspecified`. Fixed to return the parsed value's Kind as-is. `GenericRecordEntry`'s typed `DateTime` getter had the same relabel-instead-of-convert bug (`DateTime.SpecifyKind(dt, DateTimeKind.Utc)` regardless of the stored value's actual Kind) — fixed to convert (`dt.ToUniversalTime()`) only when the Kind isn't already UTC. Paired with the `SetDateTimeValue` rename above, which stopped forcing UTC at write time now that read time preserves Kind correctly. Covered by new `InternalJobMasterSerializerTests.cs`.

- **`BulkUpdateAsync(IList<JobRawModel>)` had no optimistic-concurrency check at all, across all four SQL implementations**: unlike every other write path on the repository (`Update`/`UpdateAsync`, the single-row `BulkUpdateAsync(BulkJobUpdateRequest)`), the multi-row `BulkUpdateAsync(IList<JobRawModel>)` — used by `AssignJobsToBucketsRunner`'s bulk-update step to flip claimed jobs from `OnMaster` to `InBucket` — unconditionally overwrote each row's `Version` with no `WHERE Version = @ExpectedVersion` guard, so two writers racing on the same job (e.g. a stale in-memory copy reprocessed after a partial-tick abort) could both "succeed," with the second write silently clobbering the first instead of being rejected. Traced directly to a real duplicate-execution incident during benchmark testing (the same job dispatched to two different buckets 23 minutes apart) before being fixed and verified with a purpose-built test across all three providers. Fixed: the pre-update `Version` is now captured as `expectedVersion` before being replaced, and every provider's multi-row UPDATE (base ANSI, Postgres `UPDATE...FROM (VALUES...)`, SQL Server `UPDATE...FROM...JOIN`, MySQL `UPDATE...JOIN`) now matches on `Id AND ClusterId AND Version = @ExpectedVersion`, silently dropping any row whose version doesn't match from the returned updated set rather than throwing — matching this method's existing "returns only what actually updated" contract. The base method signature changed `public` → `public virtual` so providers can share one parameter-binding helper (`AddBulkUpdateRowParams`). Covered by new conformance tests (`BulkUpdate_Models_ShouldOnlyUpdate_RowsWithMatchingVersion`, 3 matching + 3 version-mismatched rows) across all three providers.

- **`MySqlMasterDistributedLockerRepository.TryLock` could grant a lock that was still legitimately held by someone else**: unlike the Postgres/SqlServer siblings of this method, which read back the row after the upsert and compare the stored token to the one they tried to write (`RETURNING`/`OUTPUT`, `acquiredToken == token ? token : null`), the MySQL implementation decided success from `rowsAffected > 0` on an `INSERT ... ON DUPLICATE KEY UPDATE` whose `SET` clauses are guarded by `IF(expires_at < NOW(), new_value, current_value)` — intended to be a true no-op when the existing lock hasn't expired. Confirmed live against a real MySQL container (not assumed from docs): MySqlConnector reports `rowsAffected=1` for this no-op case, not 0, so `TryLock` returned a fresh token and silently granted the lock even while the previous holder's lease was still active. This was flagged as a known gap during this session's RepoConformance/Testcontainers migration but not root-caused or fixed at the time (see the `RepositoryDistributedLockerConformanceTests` entry from that migration) — it resurfaced as a `MySqlDistributedLockerRepositoryConformanceTests.TryLock_ShouldBeMutuallyExclusive_UntilReleased` failure while re-running the suite this session, and was fully root-caused this time. Fixed by bringing MySQL onto the same read-back-and-compare pattern the other two providers already use: the `INSERT ... ON DUPLICATE KEY UPDATE` is now followed by a `SELECT` of the row's current token in the same round trip, and `TryLock` only returns success if that token matches what it just tried to write — no longer depends on MySQL/MySqlConnector's affected-vs-found-rows semantics at all. This lock underpins every distributed lock in the framework (bucket locks, agent-connection locks, etc. via `JobMasterLockKeys`), so on MySQL clusters this was a real (if narrow-window) correctness gap, not just a test artifact.

- **`BulkDispatchJobsToBucketAsync` could revert an already-executing job's status back to `OnMaster`, risking duplicate execution** (`WorkerClusterOperations`, `AssignJobsToBucketsRunner`): dispatching a partition mixes two paths per job — some are short-circuited directly into the local `JobsExecutionEngine` when the bucket's engine happens to live in this same worker process (in-memory, no DB write, left `InBucket` and now actively executing), the rest go through one batched `BulkAddForProcessingAsync` call. If that batched call threw, `WorkerClusterOperations` itself correctly held only the batched subset on master — but the caller, `AssignJobsToBucketsRunner.DispatchJobsToBucketsAsync`, had its own catch around the same call that re-derived the "failed" set as the *entire original partition* (`partition.Select(x => x.Id)`) and bulk-updated all of them to `HeldOnMaster`, including any job that had already been short-circuited into the engine and was mid-execution. The next tick could then re-acquire and re-dispatch that job to a different bucket while the original execution was still running — the same class of incident as the `BulkUpdateAsync` version-check bug above, via a different path. Found by a second review pass over this release's diff, not live. Fixed on both sides: `WorkerClusterOperations.BulkDispatchJobsToBucketAsync`'s per-job short-circuit attempt is now wrapped in its own try/catch, holding only that one job on master if it fails (matching the existing per-job pattern already used for an unexpected `OnBoardingResult`) instead of letting an exception from one job abort the rest of the partition's short-circuit attempts and propagate out unattributed; the batched-dispatch failure path now uses `masterJobsService.BulkUpdateAsync(BulkJobUpdateRequest.HeldOnMaster(...), useAcquireThrottler: true)` in one call instead of a per-job update loop, matching the pattern the caller used to have. `AssignJobsToBucketsRunner`'s catch around the dispatch call no longer does any recovery of its own — `BulkDispatchJobsToBucketAsync` is now the sole, complete authority on which jobs actually need to go back to `OnMaster`, so the caller just logs.

- **NATS `connectionOptions` with only a `password` set silently produced no auth at all** (`NatsJetStreamConnectionOptionsStrategy.BuildAuthOpts`): the "was anything configured" guard checked `username`/`token`/`credentialsFile`/`nkey`/`jwt` but not `password`, so a `connectionOptions` dictionary containing only `{"password": ...}` — e.g. a username already embedded in the base connection string with the password injected separately to keep it out of a checked-in config — was read as "nothing configured," returned `null`, and the connection silently fell back to whatever auth (or none) the base connection string alone provided. Found by the same review pass. Fixed by adding `password` to the guard; no additional combination validation was added on top (an incomplete/invalid combination is left to surface as a normal connection failure rather than being pre-validated here).

- **`JobMaster.Dashboard` theme-builder parameters incorrectly typed as non-nullable**: `DashboardThemeBuilder` and its `IJobMasterDashboardThemeColorSelector`/`IJobMasterDashboardFontFamilySelector` interfaces declared several genuinely-optional parameters (e.g. `Logo`'s `content`, `BaseColors`' four color args, `SetFontSans`'s `fontUrl`) as `string` instead of `string?`, producing inaccurate nullable-reference-type warnings for callers passing `null`. No compiled/runtime dependency exists between `JobMaster.Dashboard` and the core `JobMaster` package (confirmed via `JobMaster.Dashboard.csproj` — no `PackageReference`/`ProjectReference` to it), so this ships as its own `JobMaster.Dashboard 0.0.3-alpha`, independent of the `JobMaster 0.0.10-alpha` bump. No behavior change.

### Changes
- **`ApiLogItem` message truncation**: Added a `CutMessage()` utility to `ApiLogItem` as a payload-reduction strategy, truncating the log message to the first 100 characters when requested to reduce serialization overhead under high-volume logging.

- **Worker auto-name simplified**
  Auto-generated names are now `{hostname}-{timestampId}` (e.g. `myserver-3c1a8b2`).
  Explicit names follow the same pattern: `{workerName}-{timestampId}` (e.g. `payroll-01-3c1a8b2`).
  The `workerId` for explicit names is now derived from `workerName` instead of `hostId`, making it stable and predictable.
  See [WorkersConfiguration](docs/WorkersConfiguration.md) for naming guidance.

- **Deadline runner is now a safety net only**: `HeldOnMasterDeadlineTimeoutJobsRunner`
  excludes jobs whose bucket is Active or Completing via `ExcludeBucketIds`. The drain
  path inside the engine is the primary mechanism; the deadline runner only intervenes when
  a bucket is lost or the drain fails.

- **Unified `AllBuckets` cache**: `MasterBucketService` now uses a single sentinel-backed
  `AllBuckets` cache for both `Query`/`QueryAsync` (when `allowedDiscrepancy` is provided)
  and `SelectBucketForJob`. `NotifyChanges` is always called before the DB operation, and
  both `AllBuckets()` and `Bucket(id)` sentinel keys are notified on every mutation.
  `IMasterBucketsService.Query`/`QueryAsync` now accept an optional `allowedDiscrepancy`
  parameter.

- **`MasterAgentWorkersService`**: `NotifyChanges` moved before DB operations in all
  mutating methods; missing notifications added to both `Delete` variants.

- **`JobsExecutionEngine` refactor**: extracted `FlushAuthorizedJobsAsync`,
  `EnqueueJobsAsync`, and `PullPendingJobsAsync` from `PulseAsync`; moved `shouldSkip`
  check after the Completing drain block; removed stale `ExceedProcessDeadline` guard
  inside `ExecuteJobAsync` (with `ProcessDeadline = UtcNow` set by `Onboard()` it would
  drop every job); `FlushToMasterAsync` uses `BulkJobUpdateRequest.HeldOnMaster`.

- **`ManualDrainProcessingJobsRunner`**: uses `BulkJobUpdateRequest.HeldOnMaster`.

- **`IOnBoardingControl` cleanup**: removed unused `Contains`, `Push`, `Count`,
  `PruneDeadlinedItems`, and `GetNextDepartureTime`; renamed `PruneOldDepartureItems` →
  `PullPending`.

- **`ITaskQueueControl` cleanup**: removed `AbortTimeoutTasks()` — superseded by
  `CancelAfter(Timeout)` in `TaskQueueItem.Start()`.

- **`JobRawModel`**: added `Onboard()` method; renamed `Enqueued()` → `Enqueue()`.

- **`MsgAckGuard` thread-safety overhaul**: all ack/nak methods now acquire a
  `SemaphoreSlim(1,1)` before checking `Outcome`, preventing double-ack/nak races when two
  concurrent threads handle the same message. `messageId` is now stored as an instance field
  (was passed as a parameter to every call). `MsgAckGuard` now implements `IDisposable`.

- **`NatsJetStreamRunnerBase` per-message AckProgress keep-alive**: a background task
  started in `ProcessMessageAsync` periodically calls `TryAckProgressAsync()` at
  `CalcAckProgressKeepAliveInterval(BucketBufferLeadTime)` intervals. The task is cancelled
  and awaited in the `finally` block before the final ACK/NAK to avoid a stale progress
  signal after the message is finalised.

- **`NatsJetStreamJobsExecutionRunner` backpressure pulse signal**: a `volatile
  TaskCompletionSource<bool>` `pulseSignal` gates `ProcessPayloadAsync` when the engine is
  near capacity (or randomly at 5 %), creating light backpressure that prevents the NATS
  consumer from pulling faster than handlers can process.

- **`NatsJetStreamJobsExecutionRunner` new `OnBoardingResult` handling**:
  `MovedToMaster` (debug log + return), `Invalid` (warning log, marks job `HeldOnMaster`,
  persists), and `Busy` (delegates to `TryNakBusyAsync` with exhaustion escalation).

- **`NatsJetStreamConstants` centralised timing helpers**: `CalcAckWait`,
  `CalcAckProgressKeepAliveInterval`, and `CalcMessageLockDuration` replace duplicated
  inline calculations. New constants: `AckOperationTimeout` (5 s), `HeartbeatPublishInterval`
  (10 s), `ConsumerIdleHeartbeat` (5 s), `BusyRetryDelays` ([30 s, 75 s, 3 min]).
  `DefaultDbOperationThrottleLimitForAgent` lowered from 1000 → 250.

- **`NatsJetStreamConnector` AckWait refactor**: `ackWait` now calculated via
  `NatsJetStreamConstants.CalcAckWait(bucketBufferLeadTime)` instead of a local formula.

- **`JobsExecutionEngine` staging buffer + engine lock**: `TryOnBoardingJobAsync` now
  appends to a `jobsToFlush` list (guarded by `jobsToFlushLock`); `FlushToOnBoardingControlAsync`
  batch-persists them as `Onboarded` on each pulse. A `SemaphoreSlim engineLock` serialises
  all pulse work in `PulseAsync`. A `recentlyHeldOnMasterIdsGuard` (version-matched, expires
  after `ErrorHoldDuration`) prevents re-onboarding a job just moved to master, avoiding DB
  version conflicts. `Completing` buckets immediately redirect jobs to master at onboard time.
  `PreEnqueuedAsync` (async) changed to `PreEnqueue` (sync), removing an async dependency
  from the enqueue hot path.

- **`TaskQueueControl.ShutdownAsync` race fix**: snapshot of `Tasks` now taken inside a
  lock before iteration. Boolean condition in `while` changed from `||` to `&&`.
  New `GetRunningTimeouts()` returns all running task `Timeout` values.
  New `GetIds()` returns a snapshot of all tracked IDs (waiting + running).

- **`OnBoardingControl` API simplification**: `Push` no longer takes a `departureDeadline`
  parameter — deadline enforcement moved to the engine layer. `ForcePush` removed (folded
  into the staging buffer). `PruneDeadlinedItems` removed. New `GetIds()` method returns a
  snapshot of all tracked IDs.

- **Heartbeat publisher decoupled from data messages**: `NatsJetStreamRunnerBase` now
  tracks `lastHeartbeatPublishedAt` independently and fires on `HeartbeatPublishInterval`
  (10 s) regardless of data message throughput — previously a quiet stream could delay
  heartbeat publication.

- **GUID v7 for all entity IDs** (breaking schema change): jobs, recurring schedules,
  job executions, and distributed lock records now use time-ordered GUID v7
  instead of random v4 GUIDs. Time-ordered IDs eliminate index page splits on insert-heavy
  workloads. `JobMasterRandomUtil` was updated with a cryptographic `NewGuid7()` implementation, and all three SQL provider repositories (MySQL, Postgres, SQL Server) were updated to generate v7 IDs.

- **`JobMasterRandomUtil` allocation optimizations**: Integrated a thread-safe nested generic `EnumCache<T>` inside `JobMasterRandomUtil.GetEnum<T>()` to cache enum value arrays, bypassing expensive reflection allocations during mock data generation on hot paths.

- **Dedicated Log & Job Execution Tables (Database Decoupling)**: Completely decoupled logging and job execution tracking from the high-contention generic records database tables:
  - **New Database Tables**: Introduced the dedicated `log` and `job_execution` tables, featuring concrete columns for properties (e.g. `level`, `category`, `reference_id`, `started_at`, `finalized_at`, `host_id`, `outcome`) and optimized compound indexes (`idx_log_cluster_level_timestamp`, `idx_log_cluster_category`, `idx_job_execution_cluster_job_id`) to accelerate query throughput and audit trail reads.
  - **Decoupled Repositories**: Introduced the new `IMasterLogsRepository` and `SqlMasterLogsRepository` inside `JobMaster.SqlBase` (implemented across MySQL, PostgreSQL, and SQL Server) to manage the dedicated `log` table. `JobMasterLogger` was refactored to flush structured `LogItem` batches directly to this repository, discarding the heavy `LogPayload` and generic record transformations.
  - **Transactional Execution Bindings**: Migrated `job_execution` writes directly into the `SqlMasterJobsRepository.UpdateAsync` database pipeline. Saving a job state change and appending its execution history (upon processing startup or completion) now occurs inside a **single, secure database transaction**, ensuring full atomicity and eliminating version-conflict split-states.
  - **Service Consolidation**: Removed `MasterJobExecutionService` and `IMasterJobExecutionService` entirely; their query responsibilities were absorbed by `IMasterJobsService.QueryJobExecutionsAsync(guid)` and the underlying `IMasterJobsRepository`.

- **NATS key generation standardization**: Refactored `NatsJetStreamAgentFingerprintResolver` and NATS dispatcher repositories to use the centralized framework utility `JobMasterRandomUtil.NewGuid4()` instead of raw `Guid.NewGuid()`.

- **Redesign of `IMasterJobsRepository` contract (breaking change)**: Updated the master repository contract to completely replace legacy `Upsert` methods with `Update`/`UpdateAsync` (which support a single-transaction `JobExecution` payload to prevent split-state database bugs), replace hardcoded `BulkUpdateStatus` with the new type-safe `BulkUpdateAsync(BulkJobUpdateRequest)`, and add the `ProbeForAcquireAsync` lookup.

- **Centralization of SQL Base Repositories**: Refactored the provider-specific databases (PostgreSQL, MySQL, SQL Server) to inherit directly from centralized base classes inside `JobMaster.SqlBase` (such as `SqlMasterJobsRepository` and `SqlMasterLogsRepository`). This fully eliminated thousands of lines of duplicated query-builder and DTO mapping code from individual provider repositories, ensuring high maintainability.

- **`AssignJobsToBucketsRunner` probe mechanism**: a lightweight `JobProbeResult`
  (Count + MinNextPlanExecutionAt) query runs before the full dispatch scan, enabling a
  two-tier pattern — skip the expensive scan entirely when the count is zero or the earliest
  job is not yet due. `ProbeDiagnosticResult` captures timing for observability.
  `IMasterJobsRepository` and `IMasterJobsService` gained the corresponding probe methods.

### Fixed

- **Critical: `NatsJetStreamRunnerBase` NATS consumer restart loop**: `ListenMsgsAsync`
  is now wrapped in `while (!ct.IsCancellationRequested)` so `ConsumeAsync` is automatically
  restarted if the server closes the subscription (heartbeat expiry, server restart, etc.).
  `IdleHeartbeat = 5 s` added to `NatsJSConsumeOpts` to keep the pull subscription alive
  during idle periods. This was the root cause of the 63–81 lost jobs observed in
  `SchedulerTest(1000)` — see `project_nats_ackwait_root_cause.md` for the original analysis.

- **`NatsJetStreamRunnerBase` `OperationCanceledException` handling**: a cancelled
  `ConsumeAsync` that is not a user-requested shutdown now logs and continues the restart
  loop instead of propagating. `StopConsumptionTaskAsync` catches both `TimeoutException`
  and `OperationCanceledException when timeoutCts.IsCancellationRequested`.

- **`NatsJetStreamRunnerBase` bad heartbeat no longer kills the subscription**: a
  heartbeat signature mismatch now `continue`s the inner loop instead of `return`ing, so
  a single malformed heartbeat cannot tear down the entire consumer.

- **`NatsJetStreamConnector` .NET 6 compatibility**: `#if NET8_0_OR_GREATER` changed to
  `#if NET6_0_OR_GREATER` for the `IAsyncDisposable` code path — previously the connector
  would not dispose correctly on .NET 6 or .NET 7.

- **`AckProgress` CTS independence**: the per-message `AckProgress` cancellation token
  source is now independent of the consumer lifecycle token, fixing a potential issue where
  cancelling the consumer would also cancel an in-flight `AckProgressAsync` call.

- **`TaskQueueControl` `IsTaskDead` completion treated as dead**: `RanToCompletion` is
  now included alongside `Faulted`/`Cancelled` in the dead-task check, since
  `ListenMsgsAsync` should never exit normally.

- **`ComputePostponeDuration` missing `PostponeFactor` multiplier**: the average running
  job timeout was not being scaled by `PostponeFactor` before adding `MinPostponeDuration`,
  causing the postpone window to be shorter than intended and re-triggering jobs too soon.
